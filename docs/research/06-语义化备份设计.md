# 06 · 备份文件语义化设计（原创设计稿）

> 本章为 backguard 的核心创新点设计稿，不依赖外部竞品实现，但与业界先例的对照见各节「先例」栏（由竞品调研章节补充）。
> 关联章节：[03 加密方案](03-加密方案.md)（清单加密）、[04 性能架构](04-性能架构.md)（索引设计）、[07 产品定位](07-产品定位与竞争优势.md)。

## 0. 问题定义

现有备份引擎（borg / restic / Kopia）的云端仓库对人类是彻底的黑盒：

- **物理层**：WebDAV/S3 里看到的是 `data/0/003f2a…` 这样的内容寻址哈希文件海洋，数千个碎块文件，用户「打开备份文件夹」即产生恐慌与不信任；
- **语义层**：快照名是一串时间戳（backguard 现状：`<device-id>-<class>-<YYYYMMDD-HHMMSS>`），回答不了用户最关心的问题——「**这次备份了什么？我最重要的是不是在里面？**」；
- **恢复层**：想看一眼内容必须安装引擎、记住密码、输入命令。软件本身成为恢复的单点故障。

「语义化」的目标：**让任何人在任何设备上、不安装任何软件，仅凭文件管理器就能回答三个问题**：

1. 这是哪台设备、什么时间、什么状态下做的备份？
2. 这次备份里大概有什么（类别、规模、最重要的部分）？
3. 我要拿回数据，该怎么做（一条可照抄的路径）？

设计红线：语义化**不得**以牺牲加密强度为代价——敏感元数据（完整文件名清单）仍必须加密；明文层只放「统计摘要级」信息（见 §2 分层）。

## 1. 语义分层的总体架构：四层可读性模型

语义化不是单一功能，而是一套从「裸文件系统」到「产品 UI」的分层可读性栈。低层永远自包含（不依赖高层软件可用），高层提供更好的体验：

| 层 | 载体 | 可读条件 | 回答的问题 |
|---|---|---|---|
| L0 物理布局层 | 云端目录树本身 | 裸文件管理器，无需密码 | 「我有哪些设备、哪些类别、多少次备份？」 |
| L1 清单层 | 每快照 `MANIFEST.txt`（明文摘要）+ `manifest.json.enc`（加密全量） | 明文部分裸读；全量需密钥 | 「这次备份了什么？」 |
| L2 叙事层 | 每快照 `STORY.md`（自然语言变更摘要） | 裸读 | 「这次和上次比发生了什么？」 |
| L3 索引/UI 层 | 本地索引库 + 客户端时间轴 UI | 装客户端 | 「我要的那张照片在哪个快照？」 |

关键设计决策：**L0–L2 全部自包含在云端目录里**——就算 backguard 这个软件从地球上消失，用户仍然能看懂自己的备份；**L3 是纯加速器**，可随时从 L1 清单重建（索引损坏 ≠ 数据损坏）。

## 2. L0：人类可读的物理布局

### 2.1 目录语义（时间先行的树）

现状（backguard v0）按「设备/类别」组织，快照在引擎 repo 内部。新设计将「快照身份」外置为真实目录：

```
<storage-root>/
  README.md                        ← 仓库级说明：这是什么、怎么恢复（明文）
  devices/
    MacBook-Pro-macOS15/
      profile.json                 ← 设备档案：主机名/OS/硬件/创建时间（明文，无敏感）
      config/                      ← 类别级内容存储（引擎仓库或块池）
      files/
      system/
      timeline/                    ← ★ 语义层：每快照一个可读目录
        2026/
          09/
            28/
              2100-evening/
                MANIFEST.txt       ← 明文摘要清单（§3）
                STORY.md           ← 自然语言叙事（§4）
                manifest.json.enc  ← 加密全量清单
                content.ref        ← 指向 config/files/system 内容池的指针
                restore.md         ← 本快照的恢复指引（明文）
              2130-before-travel/
                …
  .backguard/
    version                        ← 布局版本号，未来迁移用
```

规则：

- 路径段全部使用 `[a-z0-9-]` 小写安全字符，跨平台（Windows 大小写不敏感、WebDAV 编码差异）零歧义；
- 快照目录名 `HHMM-<语义标签>`：语义标签由用户输入或自动生成（§4），如 `evening`、`before-travel`、`pre-migration`；
- 时间在路径中**倒序可读**（年/月/日），文件管理器默认排序即时间轴——这是零成本获得的「时间轴 UI」，先例是 macOS Time Machine 的层叠窗口与 Nextcloud 的按年月归档。

### 2.2 设备与类别语义

- 设备目录名 `<hostname>-<OS><ver>`（沿用现状，已被验证可读）；
- 三档案语义（config/files/system）保留并**外显**到目录层：用户即使不理解术语，也能看到三个文件夹并从 `profile.json` / 仓库 `README.md` 里得到一段中文解释；
- 每个类别目录内放一个 `WHAT-IS-THIS.txt`（一次性生成，明文）：解释「config=丢了很痛的配置与密钥；files=你自己创造的文档照片；system=重建系统用的图纸」。

### 2.3 明文层与密文层的边界

明文允许（统计摘要级）：

- 快照时间、设备名、类别、语义标签；
- 文件计数、总字节数、按顶层目录/扩展名聚类的规模分布（如 `Documents: 2.1GB / 340 files; Photos: 18GB / 2,102 files`）；
- 引擎版本、布局版本、快照 ID、内容池引用。

明文禁止（隐私敏感，只进加密清单）：

- 完整文件名与路径（文件名常含人名、项目名、账号等：`房贷合同-张三.pdf`）；
- 目录树的完整形态、mtime 精细信息、扩展属性；
- 任何文件内容。

> 权衡说明：聚合统计在极端场景（用户目录里只有一个文件）仍可能泄露规模信息，属可接受残留风险；可提供「隐身模式」将 L1/L2 也整体加密，代价是裸文件管理器可读性归零。默认不开。

## 3. L1：双清单——明文摘要 + 加密全量

每个快照携带两份清单：

### 3.1 `MANIFEST.txt`（明文，摘要级，人机双读）

```text
╔══════════════════════════════════════════════════════════╗
║  backguard 快照 · MacBook-Pro-macOS15                     ║
║  2026-09-28 (周一) 21:00 · 标签: evening                  ║
║  快照 ID: snap_9f3a2c   上一次: 2026-09-27 22:10          ║
╠══════════════════════════════════════════════════════════╣
║  files    1,842 个文件 · 21.3 GB（新增 34 · 变更 12）      ║
║    Documents/  2.1 GB ·  340 文件                          ║
║    Pictures/  18.0 GB · 2,102 文件   ← 含 RAW              ║
║    Movies/     1.2 GB ·   38 文件                          ║
║  config    1,204 个文件 · 480 MB（新增 3 · 变更 41）        ║
║    ~/.ssh/  ~/.gnupg/  Keychains/  Preferences/            ║
║  system    系统图纸: 包清单 214 · 已采集                    ║
╠══════════════════════════════════════════════════════════╣
║  完整文件清单已加密存放于 manifest.json.enc                ║
║  如何恢复 → 见本目录 restore.md                            ║
╚══════════════════════════════════════════════════════════╝
```

要点：

- **ASCII 卡片框**：终端、记事本、手机文件 App 里都能保持视觉完整，不依赖任何渲染器；
- 数字千分位、中文单位、周几——「给人读」的格式化优先于机器解析（机器读 json.enc）；
- 「新增 34 · 变更 12」来自与上一快照清单的 diff，让用户感知「增量在发生、备份在活着」——对抗备份软件最大的隐性风险：**默默停摆**。

### 3.2 `manifest.json.enc`（加密，全量，机器读）

结构（解密后）：

```json
{
  "format": "backguard/manifest/1",
  "snapshot": {"id": "snap_9f3a2c", "parent": "snap_71b0ee", "started": "...", "finished": "..."},
  "device": {...},
  "classes": {
    "files": {
      "entries": [
        {"p": "Documents/2026-09 报销/发票-0912.pdf", "s": 231144, "m": 1727433600,
         "h": "blake3:…", "chunks": ["…"], "xattr": "enc:…"}
      ]
    }
  },
  "stats": {...}
}
```

- 加密方案遵循 [03 章](03-加密方案.md)：`age`-style XChaCha20-Poly1305，仓库主密钥包裹；
- 它同时是**恢复引擎的完整账本**：有了它 + 内容池，恢复不需要原引擎仓库结构也能逐文件重建（为「逃生恢复」兜底）；
- 与 L3 本地索引的关系：本地索引是它的缓存与聚合视图，损坏可由全部快照的 json.enc 重建。

## 4. L2：STORY.md——自然语言变更叙事（核心差异化）

### 4.1 动机

时间戳 + 统计仍然是「数据」，不是「记忆」。用户对自己数据的心智模型是事件式的：「日本旅行回来那天」「换电脑之前」「项目交付那晚」。让每次备份携带一段**自动生成的中文叙事**，是把「文件海洋」变成「日记」的关键一步。

### 4.2 生成机制（规则模板，不依赖 AI，AI 可选增强）

输入：本快照与父快照的加密清单 diff + 路径语义分类。

处理流水：

1. **变更聚类**：把 diff 的文件按「共同前缀目录」聚类（取变更量 ≥N 或字节占比 ≥P 的簇）；
2. **簇分类**：对簇的路径打语义标签（可扩展表）：`Photos（RAW/IMG_/DCIM/截图）`、`Documents（doc/pdf/xlsx）`、`Code（git 仓库特征：.git 目录变更）`、`Downloads`、`Credentials（.ssh/.gnupg）`、`System`；
3. **显著性排序**：按「新增字节 × 类别权重 × 稀有度」排序，取 Top 3 簇；
4. **模板渲染**（确定性，无幻觉）：

```markdown
# 2026-09-28 21:00 · evening

这次备份相比昨天 22:10：

- 📷 新增约 **214 张照片 / 1.2 GB**，集中在 `Pictures/日本旅行-0926`（其中 RAW 38 张）；
- 📄 修改了 **3 个文档**：`Documents/2026-09 报销/`（发票-0912.pdf 等）；
- 🔑 密钥环有变化：`Keychains/login.keychain-db` 更新（可能改过密码）。

总增量 1.4 GB，用时 6 分钟。至此你已连续备份 46 天。/device: MacBook-Pro-macOS15
```

5. **AI 增强（可选、本地、默认关）**：将聚类结果交给本地小模型润色为更自然的一句话；规则层保证「事实永远来自清单 diff」，AI 只改写措辞不产生事实——规避幻觉风险。

### 4.3 敏感性处理

- STORY.md 属明文层 → **只出现目录名与统计**，不出现完整文件名（目录名如 `日本旅行-0926` 已在聚类层截断到 Top-3 簇的顶层名，且遵循「隐身模式」整体关闭）；
- 目录名本身敏感的判断：`Credentials` 类簇一律只写数量不写名字。

### 4.4 价值论证

- 把「备份了什么」从检索问题变成阅读问题——小白用户第一次能**看懂**自己的备份；
- STORY 序列构成一份免费获得的「数字生活时间线」，附带情感价值（类似 Google Photos 的「回忆」，但完全本地、零上传画像）；
- 对专业用户：它是人肉可审计的变更日志（audit trail），发现异常变更（密钥环变动、意外删除）的第一入口。

## 5. L3：本地索引与时间轴 UI（客户端）

- 本地 SQLite（或 redb）索引：快照元数据 + 解密后的清单条目 + 全文索引（文件名 FTS5），支持「输入文件名 → 哪个快照有它」秒级检索；
- 时间轴视图：纵轴时间、横轴类别，密度热力显示数据量——Time Machine 式的「回到过去」心智，但跨设备聚合（所有设备一条时间线）；
- 挂载浏览（FUSE/macFUSE/WinFsp）作为进阶能力：快照即只读目录。

## 6. 逃生恢复（Disaster Recovery without backguard）

语义化的终极测试：**软件死亡，数据不死**。

1. 云端根 `README.md`（明文）写明：目录含义、快照结构、`manifest.json.enc` 的格式文档（schema 版本化）、以及「如何用任意 age 实现 + 内容池手动恢复」的完整步骤；
2. 每个设备目录放一份 `backguard-rescue` 单文件恢复器（Rust 静态编译，~10MB，三平台各一份；或引导用 `curl | sh` 脚本）——不依赖原安装；
3. `content.ref` + `manifest.json.enc` 构成自描述对：内容块内容寻址（blake3 命名），恢复器只需「拉块 → 解密 → 按 json 重建路径」；
4. 每年（或每 N 个快照）自动写入一个 `rescue-test` 记录：上次逃生演练的时间与结果，防止「以为能恢复」的假安全。

## 7. 与 backguard v0（脚本方案）的迁移兼容

- v0 的 borg/restic 仓库可以原样并入新布局：`config|files|system` 目录即引擎仓库，`timeline/` 层新增生成；
- 迁移工具扫描现有 borg/restic 快照 → 反向生成 `MANIFEST.txt`（borg `--json` / restic `snapshots --json` 可导出文件列表）→ 追加到 timeline；
- 设备命名规范不变，云端「只增不减」策略不变。

## 8. 开放问题（留待原型验证）

1. 明文摘要中顶层目录名的暴露边界：默认取「用户主目录下一级」，是否需要白名单（只显示 Documents/Pictures 等标准目录）？
2. STORY.md 生成的聚类参数（N/P/Top-K）在极端目录形态（百万小文件、单一大文件）下的退化行为；
3. 时间目录层级（年/月/日）在高频备份（每小时）下的目录爆炸——考虑日目录内 `HHMM` 前缀排序即可，或「小时快照折叠进当日 STORY 的多段」；
4. Windows 设备名的字符安全化（hostname 可能含中文/空格）已有方案，但需 fuzz 测试 WebDAV 各家实现；
5. 隐身模式下 L0 是否退化为纯哈希目录（与普通加密备份无异）→ 需要产品层明示两种模式的取舍。
