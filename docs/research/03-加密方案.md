# 03 · 加密方案调研：文件级/块级加密备份的选型论证

> 调研时间：2026-09。方法：直接核读 restic/Borg/Kopia/Duplicacy/age 规范与源码、NIST/OWASP/IETF 文档、学术论文。
> 关联：[06 语义化设计](06-语义化备份设计.md)（清单加密边界）、[04 性能架构](04-性能架构.md)（压缩/加密顺序）、[05 云端多端](05-云端多端与传输.md)。

## 0. 执行摘要

备份加密的业界共识已经收敛：**内容定义分块（CDC）→ 压缩 → 每块 AEAD 加密 → keyed MAC 作为对象 ID → 口令只用于包裹随机主密钥（envelope）→ 本地/仓库内加密索引承载可搜索性**。算法层面双轨制（有 AES 硬件加速用 AES-256-GCM/OCB，无则 ChaCha20-Poly1305）已有 Borg 2 与 Kopia 两个成熟先例。backguard 在此骨架上补齐三块业界尚薄弱的能力：Argon2id KDF（Borg 2 已先行）、强制恢复码（Apple ADP 先例）、ML-KEM 混合包裹（age 规范已先行）。

## 1. 对称加密选型

### 1.1 AES-256-GCM vs ChaCha20-Poly1305

**性能结论**：备份是大块顺序流，瓶颈几乎总在存储 I/O 而非密码学；但单核加密吞吐仍决定低端 NAS/树莓派类设备的体验。

- x86 AES-NI / ARMv8 Cryptography Extension（含 Apple Silicon）上，AES-GCM 硬件加速吞吐 GB/s 级，快于纯软件 ChaCha20。
- 无硬件 AES 时反转：restic 贡献者 rfjakob 在 [restic#628](https://github.com/restic/restic/issues/628) 的实测：AES-CTR+Poly1305 比 Go 内建 GCM 快约 50%（258 vs ~180MB/s 软件路径），而有 AES-NI 时 GCM 达 739MB/s（4KiB 块）。restic 作者 fd0 解释当年选 CTR+Poly1305 而非 GCM 的原因：早期 Go 无优化 GCM 实现 + Poly1305 论文更易审读。
- ChaCha20-Poly1305 纯软件实现 constant-time，无 cache 计时侧信道，这是 armv7/旧 x86、无 CE 的 ARM SoC 上的正确选择。
- Borg 2 直接把选择交给运行时探测：`--encryption (aes256-ocb|chacha20-poly1305)` 二选一——AES-256-OCB 用于硬件 AES 场景（单遍、认证加密），chacha20-poly1305 用于纯软件场景。

### 1.2 AEAD nonce 管理陷阱（备份场景的核心风险）

- **随机 96-bit nonce 的碰撞**：NIST SP 800-38D §8.3 规定同一密钥下随机 IV 的 GCM 调用不得超过 2^32 次。备份库的 chunk 数量恰好会逼近这个量级：一个活跃多年的 dedup 库存 10^8–10^9 块很正常，且密钥是长期单主密钥派生——这正是「随机 nonce GCM」最坏的使用方式。GCM 一旦 nonce 复用是灾难性失败（认证密钥可恢复 + 计数器重用导致明文 XOR 泄露）。
- **XChaCha20 的 192-bit nonce**：生日碰撞界 2^96，随机 nonce 可安全用于海量块，无需全局计数器（[XChaCha 草案](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha)，虽为 Informational 草案但 libsodium/Go x/crypto 等已事实标准化）。
- **Borg 2 的工程化解法（更优雅，值得直接借鉴）**：每次进程调用生成随机 session id → HKDF 派生 session key，IV 用会话内从 0 递增的计数器。文档原话："IVs (nonces) do not need long-term special care here as they did for the legacy encryption modes"——长期单密钥的 nonce 管理问题被结构性消除。
- 备选：AES-GCM-SIV（RFC 8452）抗 nonce 误用，但备份产品中尚无采用先例，库支持面也弱，不建议首选。

### 1.3 备份界实证（逐家核实）

| 工具 | 加密 | 认证/ID | KDF | 备注 |
|---|---|---|---|---|
| **restic** | AES-256-CTR | Poly1305-AES（EtM，`IV‖CT‖MAC`，每文件随机 16B IV，开销 32B） | scrypt N=65536,r=8,p=1 | key file=JSON+scrypt 包裹的 master keys；支持多口令（每口令一个 key 文件）；**v2 仓库（0.14+）只加了 zstd 压缩，并未切换 AEAD**；缓存目录也加密 |

| **Borg 2** | **AEAD：AES-256-OCB 或 ChaCha20-Poly1305**（按硬件选择） | id-hash 可选 keyed SHA-256/BLAKE3 | **Argon2id**（随机 128-bit salt） | session key+计数器 IV；移除 `none` 模式；多把 borg key 包裹同一密钥材料 |

## 2. 密钥体系设计

### 2.1 KDF：Argon2id > scrypt > PBKDF2

[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) 优先级：**Argon2id 首选**；不可用时 scrypt；遗留 bcrypt；FIPS 合规才用 PBKDF2。具体参数：

- Argon2id 五档等价配置任选：m=47104KiB/t=1、**m=19456KiB(19MiB)/t=2/p=1（最低推荐）**、m=12288/t=3、m=9216/t=4、m=7168/t=5，p=1。
- scrypt 最低 N=2^17(128MiB)/r=8/p=1（注意：restic/kopia 现用的 N=65536=64MiB 已低于该档，属历史遗留）。
- PBKDF2-HMAC-SHA256 需 600,000 次迭代。

实证：**Borg 2 已从 PBKDF2 迁移到 Argon2id**；restic/kopia/age 仍用 scrypt；Duplicacy/Borg 1.x 停留在 PBKDF2。新品无历史包袱，应直接 Argon2id（Rust 侧 `rust-argon2`；注意移动端内存档位可调）。

### 2.2 分层密钥（envelope）：为什么必须

全部主流产品的同构设计：**随机主密钥（DEK/数据密钥）↔ 口令只派生 KEK 去包裹它**。

- restic：scrypt(口令) 解开 key 文件中的 master encrypt/MAC keys；一库多 key 文件，各自独立口令，改口令=加一个 key 文件、删旧 key 文件，**数据零重加密**（文档明确 "A repository can have several different passwords"）。
- Kopia：明文写出 envelope 结构——口令→scrypt→Km，HKDF 按 purpose（"AES"/"CHECKSUM"）域分离派生子密钥。
- Borg 2：多把 borg key、各自口令、包裹同一密钥材料。
- age：file key（16B）+ 多 stanza（X25519/scrypt/插件）包裹，同一文件多接收者零重加密。

推论：**换口令 O(1)（只重写一个小密钥文件）**、多设备/多口令共存、旧口令可吊销。backguard 必须采用，且子密钥用 HKDF-SHA256 按 purpose 域分离（Kopia 先例：加密/ID 独立密钥；Borg 原文："Every operation … uses independent, random keys"）。

### 2.3 密钥恢复：「密码丢失=全丢」的行业现状与缓解

现状：E2EE 备份产品普遍存在丢失口令即丢库问题。Apple 是做得最完整的消费级样本（[iCloud 数据恢复选项](https://support.apple.com/en-us/102651)）：

- 开启 Advanced Data Protection 后 "Apple will not have the encryption keys to help you recover it"，**强制用户先设置至少一个恢复方式**；恢复途径=设备密码 / **Recovery Contact（社交恢复，消费级唯一大规模落地）** / **Recovery Key（纸质/离线恢复码）**；三者全失则数据不可恢复。
- 1Password 同思路：账户口令 + 128-bit Secret Key，交付时打印纸质 Emergency Kit（高熵秘密的物理备份形态）。
- **Shamir 秘密分享（SSSS）**：消费产品中由硬件钱包生态落地——Trezor 的 [SLIP-39](https://github.com/satoshilabs/slips/blob/master/slip-0039.md) 实现两级分片（组间 G-of-GT + 组内 T-of-N，1≤各参数≤16），动机原文直指"备份持有者可能携资产潜逃"的单点托管风险；助记词带 RS1024 校验（≤3 词错误可检出）。通用备份软件（restic/borg/kopia）**均无内置 SSSS**——这是 backguard 可形成差异化的空位。
- 建议：恢复码（高熵、直接 HKDF 包裹）设为强制项（Apple 先例：不允许无恢复途径进入 ADP）；SSSS 可作为高级选项。
- **密码管理器作为第 2 份副本（冗余增强，非替代）**：borg/restic 原生支持 `BORG_PASSCOMMAND`/`RESTIC_PASSWORD_COMMAND` 外部取口令，rbw（非官方 Bitwarden CLI，agent 常驻）是社区标准集成（配方见 05 §7）。红线：vault 里的恢复材料只算纸质恢复码的第 2 份副本——灾难场景（账户锁定、主密码遗忘）恰是密码管理器不可用之时，多路径「任意一条独立可用」的论证不容单点化；vault 材料的可用性由周期性 drill 真实验证（08 章 T3.4 `--from-bitwarden`），不做静默假设。

## 3. 文件级 vs 块级加密

### 3.1 CDC 后逐块加密 vs 整文件加密

- 四大备份工具（restic/borg/kopia/duplicacy）全部是 CDC+逐块加密：增量与去重在块粒度、恢复可并行、坏块影响局部化。整文件加密（Cryptomator、gocryptfs 的挂载式 FUSE 方案）面向同步盘场景，不支持跨版本 dedup。
- 权衡：逐块加密每块承担 nonce+tag 开销（16+16B，平均 1MiB 块下 ~0.003%，可忽略）；块越小去重越好但元数据膨胀——业界稳定在平均 0.5–2MiB 可变块。

### 3.2 收敛加密的安全缺陷与缓解

- 理论定式：Bellare/Keelveedhi/Ristenpart 将其形式化为 Message-Locked Encryption——"the key under which encryption and decryption are performed is itself derived from the message"（[eprint 2012/631](https://eprint.iacr.org/2012/631)，EUROCRYPT 2013）。固有缺陷：**确认攻击/字典攻击**——对低熵文件（大众操作系统文件、常见文档），攻击者可离线加密候选明文、比对密文确认某文件已被存储，甚至全库解密。
- 缓解谱系：
  1. **per-repo/per-user salt + keyed chunk ID（主流方案，全体备份工具采用）**：Borg 明确论证 chunk ID 必须是 keyed MAC——"若用普通 sha256，攻击者可为已知小文件算哈希比对仓库"；且 buzhash 分块器用 per-repo 密钥 seed 决定切分点，攻击者连块边界都无法复现，另提供 `obfuscate` 伪压缩器对抗基于 chunk 大小的指纹。代价：**放弃跨用户全局去重**，只保留单库内 dedup——这是安全与商业（云商侧 dedup）的自觉切割。
  2. **Oblivious dedup（服务器辅助）**：DupLESS（USENIX Security 2013，[eprint 2013/429](https://eprint.iacr.org/2013/429.pdf)）用独立 key server 经 OPRF（RSA 盲签名）在线派生 message-based key：key server 不知道文件内容、客户端无法离线穷举，字典攻击被限速到 OPRF 交互速率。学术界后续延续该线，但**无主流消费备份产品部署**。
- 结论：backguard 采用 per-repo salt + keyed ID（放弃跨用户 dedup）即可宣称与 restic/borg/kopia 同级的安全论证；跨用户 dedup 不值得为存储成本引入在线密钥服务。

### 3.3 文件名/目录结构加密

- restic/borg/kopia 路线：目录树整体作为对象加密存储（树对象也按 keyed hash 寻址），云端只见随机字节名的 blob，**路径结构零泄露**；父子关系只在解密后的树对象内。恢复性由「快照→根树 ID」链保证。
- Cryptomator 路线（[security architecture](https://docs.cryptomator.org/en/latest/security/architecture/)）：逐文件名 AES-GCM 加密、目录元数据内联，面向挂载盘随机访问。
- Duplicacy 反例：chunk 文件名=chunk ID 暴露（其 wiki 明言 "Chunk ids … therefore exposed"，但 ID 是 keyed 的，信息量有限）。
- backguard 应走树对象路线；文件名绝不进云端索引（与 [06 章 §2.3](06-语义化备份设计.md) 明文/密文分层边界呼应）。

### 3.4 压缩与加密顺序

- 铁律先压缩后加密（密文高熵不可压）。实证：restic v2 blob 级 zstd（明文以 encoding version header 开头）；Borg 加密输入即 `compressed`；Kopia 同序。
- CDC 块粒度影响压缩率：小块（<1MiB）zstd 无法跨块建字典。缓解：zstd 长模式/训练字典或按 pack 聚合压缩（restic pack 内多 blob 共享压缩上下文的权衡仍在社区讨论）。

## 4. 验证与完整性

- 单块完整性由 AEAD tag 保证，但**全库可验证性必须独立设计**（bitrot、后端静默损坏、勒索替换）：
  - restic：`restic check` 读全部 pack、校验 blob hash/结构重建索引。
  - Kopia：CLI 有 `kopia content verify` 与 `kopia snapshot verify`，支持下载远程数据比对 hash，防静态 bitrot。
  - Borg：`borg check --verify-data` 走 HMAC 全量校验。
- 内容寻址（keyed hash 作 ID）本身构成类 Merkle 结构：任何块被篡改/损坏在读取或 check 时必然 tag/hash 失配，不可静默通过。建议 backguard：每块存（keyed 明文 hash 进加密索引）+（AEAD tag 随块走），check 分两档：结构校验（本地缓存可做）与数据校验（下载后逐块验证）。
- **可搜索性困境**：密文上按文件名/类型检索在实用上不可行（SSE 的访问模式泄露下限已知，见 §5.2）。业界统一答案：**索引加密后存云端、同步到本地解密后检索**。restic 索引/缓存均加密（"The cache is also encrypted to prevent metadata leaks"），kopia 本地维护 index 缓存。云端只看到密文索引 blob。backguard 应内置「本地加密索引缓存 + 云端加密索引 blob」，检索永远发生在本地。

## 5. 前沿方向

### 5.1 后量子（PQ）

- ML-KEM 已定稿：FIPS 203 于 **2024-08-13** 发布，参数 ML-KEM-512/768/1024，"believed to be secure, even against adversaries who possess a quantum computer"（[NIST FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)）。
- 备份的特殊性：**冷备份的保密期横跨量子时代**——"harvest now, decrypt later" 对 10–30 年保存期的备份库是最贴切的威胁模型（消息通信只需保护会话期）。而 PQ 迁移在备份里成本极低：只需把 DEK 多包一层混合 recipient，数据层无需重加密。
- 消费生态佐证：Apple iMessage PQ3、Signal PQXDH 均已上线混合 PQ。
- **直接先例**：age 规范已定义 **mlkem768x25519（X-Wing 混合）recipient（`age1pq`）** 及 mlkem768p256tag（PQ+硬件混合），并建议同一文件不要同时加密给 PQ 与非 PQ recipient（避免安全降级到弱 recipient）。
- 建议：backguard 的 DEK 包裹层同时写 X25519 stanza 与 ML-KEM-768 混合 stanza（或直接 X-Wing），一次到位。

### 5.2 FHE / 可搜索加密（SSE）

- SSE 自 Song-Wagner-Perrig(2000)、Curtmola et al.(2006) 以来研究充分，但泄露访问模式/查询模式的下限已知；FHE 计算开销对 PB 级备份不现实。**没有任何主流备份产品将 SSE/FHE 用于密文检索**——Dropbox/Backblaze/iCloud 的做法都是本地明文索引或 E2EE+本地索引。结论：2026 年做产品，SSE 不可行；「本地加密索引」即是答案。

### 5.3 硬件密钥

- 直接先例：[age-plugin-yubikey](https://github.com/str4d/age-plugin-yubikey)——私钥存 YubiKey PIV retired slot（ECDSA P-256），身份文件只含查找信息；解密必须硬件在场（PIN/touch policy 可配）；age 与 rage 均支持。C2SP 规范进一步把 p256tag 定为标准 recipient 类型（硬件密钥成为一等公民，且已有 ML-KEM+P-256 混合版）。
- 平台侧：Apple ADP 的密钥锚定在设备/Secure Enclave；Android Keystore StrongBox 提供 equivalent。backguard 三平台用法应遵循 age 模式：**硬件密钥作为 DEK 的一个 wrap stanza**（而非替代口令），iOS 用 Secure Enclave 包裹、macOS/Windows 用 TPM/Keychain/DPAPI、桌面外接 YubiKey 走 PIV/FIDO2。

## 6. backguard 推荐加密架构（每步附业界先例）

```
┌─ 口令 P（人类）                     ┌─ 恢复码 R（高熵 128-bit，强制设置）
│                                    ├─ YubiKey/Secure Enclave（P-256 stanza）
│                                    └─ ML-KEM-768+X25519 混合 stanza（PQ）
└──────────┬─────────────────────────┴──────────┬──────────
           ▼                                    │
   Argon2id(m≥19MiB,t≥2,p=1)     高熵项直接 HKDF │   ← OWASP；Borg 2 已用 Argon2id
   → KEK_passphrase                          │      age：多 stanza 包裹同一 file key
           └────────────┬────────────────────┘
                        ▼
          解包/包裹 DEK（随机 256-bit repo master key）
                        │ HKDF-SHA256 按 purpose 域分离
        ┌───────────────┼────────────────┬──────────────────┐
        ▼               ▼                ▼                  ▼
   K_chunk_enc    K_chunk_id        K_tree_enc         K_index_enc
  （数据加密）  （keyed HMAC 做    （目录树/文件名    （加密索引：
                对象 ID）           加密）              本地缓存+云端 blob）
                        │
   数据面：CDC 分块（keyed seed 分块器）
   → zstd 压缩（先压缩）                    ← restic v2 / Borg / Kopia 同序
   → 每块 AEAD：
     · 硬件 AES 探测命中 → AES-256-GCM（或 OCB）
     · 未命中 → XChaCha20-Poly1305（192-bit 随机 nonce）
     · 或 Borg2 式 session key+计数器 nonce        ← Borg 2 / Kopia 双算法先例
   → chunk 对象名 = HMAC(K_chunk_id, plaintext hash)
                        │
   完整性面：AEAD tag + 索引内 keyed hash
   → check（结构校验）与 verify（下载数据逐块校验，防 bitrot）  ← restic check / kopia verify
```

逐项决策与先例：

1. **每块 AEAD，双算法自适应**（AES-256-GCM@硬件加速 / XChaCha20-Poly1305@软件路径；nonce 用计数器或 192-bit 随机，规避 NIST 2^32 随机 nonce 界限）——先例：Borg 2（OCB|ChaCha20-Poly1305）、Kopia（GCM 默认+CHACHA20-POLY1305 可选）。
2. **Argon2id 派生 KEK 包裹随机 DEK**，多 stanza（口令/恢复码/硬件/PQ）并存，改口令零重加密——先例：restic 多 key 文件、Borg 2 多 borg key、age 多 stanza、Kopia envelope。
3. **HKDF 域分离子密钥**（加密/ID/树/索引各自独立）——先例：Kopia（"AES"/"CHECKSUM" purpose）、Borg（independent random keys per operation）。
4. **keyed HMAC chunk ID + keyed 分块 seed**，放弃跨用户 dedup，明确防确认攻击论证——先例：Borg（1.x 与 2 均有）、restic、Kopia。
5. **先 zstd 后加密**——先例：restic v2、Borg、Kopia。
6. **目录树对象加密（文件名零泄露）+ 加密索引本地缓存**——先例：restic（cache 也加密）、kopia 本地 index。
7. **强制恢复码 + 可选 SSSS 高级分片**——先例：Apple ADP（强制恢复途径）、1Password Emergency Kit、Trezor SLIP-39（两级 Shamir）；社交恢复可选 Apple Recovery Contact 形态。
8. **PQ 一次到位**：DEK 加 X-Wing（mlkem768x25519）混合 stanza——先例：age `age1pq` recipient。
9. **check/verify 双档全库校验**——先例：restic check、kopia content/snapshot verify、borg check --verify-data。

**差异化机会**：Argon2id+强制恢复码+PQ 混合包裹的组合目前没有任何一款消费备份工具完整提供（Borg 2 有 Argon2id 无 PQ；age 有 PQ 无备份语义；Apple ADP 有恢复体系但闭源且密钥体系不透明）。
