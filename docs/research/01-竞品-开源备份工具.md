## 1. Restic

**核心机制**：CDC 用 Rabin 指纹（64 字节滑窗，多项式随机化存入 config 抗水印攻击）；<512KiB 文件不分块，平均块 ~1MiB（512KiB–8MiB）。blob 打包进 pack 文件，repo v2 要求数据/树 blob 分包，可流式写入。加密 AES-256-CTR + Poly1305-AES，`IV||密文||MAC` 每文件 32 字节开销；口令经 scrypt 派生 64 字节解包主密钥，**支持一库多口令/keyfile**（改密码不需重加密）。压缩仅 zstd（repo v2 起）。索引为 JSON（可 zstd），<8MiB/文件，映射明文哈希→pack/偏移；本地按 repo 缓存快照/数据/索引。锁分排他/非排他，>30 分钟视为 stale（[设计文档](https://restic.readthedocs.io/en/stable/100_references.html)）。

**后端**：local、SFTP、REST、rclone，以及官方集成版直接支持 S3（含 R2 等 S3 兼容）、Azure、GCS、B2。

**恢复**：`restic mount` FUSE 浏览、`restore` 单文件/子目录、跨平台（Go 单二进制）。HN 用户好评点正是「快照=增量速度+全量语义 + 可挂载浏览」（[HN 41829913](https://news.ycombinator.com/item?id=41829913)）。

**痛点**：
- prune 慢出名："Pruning takes forever in Restic, which is why we migrated away"；索引格式慢、Rabin 分块 "very slow compared to more recent alternatives"。
- 无原生配置文件/GUI，用户被迫用 borgmatic 式脚本或第三方 Backrest/autorestic/resticprofile；Backrest（WebUI 编排器）2026-06 上 HN 98 分，评论「restic 是 CLI-only 无 GUI 这个生态位被它填补」（[HN 48370278](https://news.ycombinator.com/item?id=48370278)）——印证 GUI 是官方长期空白。
- prune 需独占锁会阻塞其他客户端；Duplicacy README 直接点名这一点做对比。
- 无对象锁（Object Lock）防勒索/防凭据泄露后删库；无 ECC/纠删码；无免密模式。
- 仓库=哈希海洋，恢复依赖「一个能跑的 restic + 正确密码」，用户明言风险。
- 准实时备份 feature request 挂了 5 年。

**性能**：中庸。大批块设备规模（千级 RBD）「根本跑不动」；社区共识 restic/Kopia 云备份资源占用中等（~100–500MB RAM），Borg 本地最快。

**Rustic**：Rust 重写，加 .gitignore、冷存储、配置文件支持，官方定位 beta（v0.11.4，2026-08-18，[GitHub](https://github.com/rustic-rs/rustic)）。

## 2. BorgBackup

**核心机制**：CDC 用 **buzhash**，块参数可调；客户端 RAM 中维护 chunks index + files cache（规模∝块数），files cache TTL 默认 20 用于跳过未变文件。加密模式创建时锁定不可改：AES-CTR-256 EtM + HMAC-SHA256 或 BLAKE2b 认证，密钥位置分 repokey（库内）/keyfile（客户端 `~/.config/borg/keys`，**丢 key=丢库，官方要求离线备份 key**）；`authenticated` 模式只认证不加密。压缩 lz4/zstd/zlib/lzma。**Borg 2.0（beta）重构仓库到 borgstore：块并入 ~50MB pack 文件**（代价：单块不可删，compact 只能整 pack 回收），新增 rclone:/s3:/b2:/rest:/http(s) 直连后端、YAML 配置文件、`borg webdav`、`borg transfer --from-borg1` 迁移（[2.0 文档](https://borgbackup.readthedocs.io/en/2.0.0b24/usage/general.html)）。

**后端**：1.x 实际只有 SSH/local（云需 rclone 桥接）；2.0 起大幅扩展。

**恢复**：FUSE 挂载（Linux/macOS；**官方 macOS 二进制不带 FUSE**）；`borg mount`/`extract` 单文件恢复；跨架构恢复 OK，但**无原生 Windows 客户端**——这是它三平台梦的致命伤。

**痛点**：
- Windows 不支持（实验性），GUI 生态（Vorta 无 Windows、Pika 仅 Linux）跟着残缺；HN 评论：Borg「互联网上数据损坏抱怨最少」，但 macOS/Windows 支持与 UI 生态落后 Kopia（[HN 37526477](https://news.ycombinator.com/item?id=37526477)）。
- 从历史快照删除特定文件「人机工学糟糕」；多主机共享仓库需谨慎。
- 内存大（chunks/files index 常驻 RAM，服务端还要加载 repo index）；锁依赖文件系统 rename 语义，FAT 强烈不建议。
- 2.0 破坏性换库格式，迁移成本引发观望。

**性能**：本地/SSH 场景公认最快；小文件大目录场景受 files cache 加速，但 RAM 占用最高。

## 3. Kopia

**核心机制**：四层架构——BLOB 存储 → 内容寻址块存储（CDC，块典型 ≤20MB，块 ID=SHA256/BLAKE2S 哈希，小块合并为 20–40MB pack，**pack 文件名随机不泄露任何内容**；`p`/`q`/`x` 前缀分数据/元数据/索引；索引损坏可从每个 pack 尾部内嵌的本地索引恢复）→ 对象层（大对象跨块+间接 JSON）→ manifest 层（快照/策略）。加密 **AES-256-GCM-HMAC-SHA256 或 ChaCha20-Poly1305-HMAC-SHA256**（内容级，且带 ECC 纠错选项）。压缩内容级可选（[architecture](https://kopia.io/docs/advanced/architecture/)）。

**后端**：S3 及兼容、Azure、B2、GCS、WebDAV、SFTP、rclone 桥接（实验性）、本地/NAS、**自建 Repository Server**（多机集中管理）。后端矩阵为 CLI 工具中最强，且**唯一官方提供跨平台 GUI（Kopia UI，Electron）**。

**恢复**：FUSE 挂载（macOS/Win/Linux）、单文件恢复、跨平台。亮点：**S3 Object Lock** 勒索防护（restic 没有），被 Velero/Kanister 采用，Veeam 有贡献。

**痛点（真实案例多）**：
- **恢复失败案例**：200GB 单文件恢复 20 小时无进度提示后失败；32GB 目录恢复失败；UI 每隔几天与仓库断连；另一用户恢复「失败且极慢」，换回 restic（[HN 37526477](https://news.ycombinator.com/item?id=37526477)）。
- **维护作业吃资源**：80TB 用户报告 maintenance 占 **120GB RAM、跑 5 小时**，本地缓存「变得巨大」，维护期下载流量暴涨。
- **元数据缺陷**：非 UTF-8 路径存错、**xattr 不存**（丢 SELinux 标签）等已知开放 issue。
- Windows VSS 只靠「几个我搞不定的脚本」支持。
- 外部 PR 合并慢、文档「S3 中心主义」。
- v0.23.1 修复「罕见竞态可能导致数据丢失」（#5371）——竞态导致数据丢失这种级别的 bug 说明核心仍有坑。

**性能**：去重率高、日常增备快、GUI 友好；但大库 maintenance/索引重建是重量级操作，缓存无上限管理是常态抱怨。

## 4. Duplicacy

**核心机制**：**Lock-Free Deduplication**——无锁、无中心块数据库，多机可并发备份同一存储并跨机去重、互不通信；删除旧快照用「两步 fossil 收集算法」（先标记化石、二次确认后删除）。变长分块（对比 Duplicati 定长分块「破坏去重」）；每块独立以哈希为文件名存储（不打包），因此天然支持 RSA 非对称加密与纠删码（[duplicacy.com](https://duplicacy.com/)、[GitHub README](https://github.com/gilbertchen/duplicacy)）。

**后端**：最广之一——本地、SFTP、S3、Wasabi、DO Spaces、GCS、Azure、B2、Dropbox、Google Drive、OneDrive、Hubic、Swift、WebDAV(beta)、pCloud、Box、File Fabric。

**恢复**：CLI/Web GUI 单文件恢复、跨平台；无 FUSE 挂载（GUI 版有快照树浏览）。

**痛点**：
- **授权争议（结构性）**：Fair Source 许可——个人免费、企业收费（现 CLI 商用 $50/台/年）；HN 上被指「听起来像开源的私有许可」「重新包装私有软件」、有人向 GitHub 举报「商业软件伪装开源」（[HN 14506673](https://news.ycombinator.com/item?id=14506673)）。GUI 收费且 "feels really clunky for something asking for cash"。
- **活跃度疑虑**：CLI 上次 release 2025-05（v3.2.5）；2026-08 论坛热帖 "Is Duplicacy no longer maintained?"（[forum](https://forum.duplicacy.com/)）。核心开发者单人项目风险。
- 2026-07 披露恢复安全漏洞：**stale symlink 可导致恢复时写出仓库外路径（CWE-59）**；另有 "missing chunks" 类数据完整性求助帖。
- 无中心索引 = check 全量校验（`check -chunks`）在云后端上流量/时间巨大，是论坛长期抱怨主题。

**性能**：官方基准宣称优于 restic/duplicity/bup/Attic；变长分块+不打包使云后端小对象多、LIST 请求多，冷启动慢是社区常识；内存占用低。

## 5. Duplicati 2

**核心机制**：定长分块（默认 100KB，可调）+ 本地 SQLite 数据库管理块索引；AES-256 加密；Web UI 全平台。定长分块对插入/删除字节敏感、破坏去重。

**痛点（HN 278 分 188 评论专帖 [HN 33449574](https://news.ycombinator.com/item?id=33449574)）**：
- **本地 SQLite 数据库慢性病**：「数据库不可逆损坏，只能换 restic（restic 只有索引和数据包，还能修复）」；「~1.5 年后损坏，永远查不出原因」；「反复要求从远端重建本地数据库，从未成功」。
- **恢复不可信**：「恢复耗时呈指数增长，直到永远完不成」；中断首备可能「静默损坏归档，而你已经依赖它好几个月」。
- **永 beta**：2.0 beta 多年——「哪个傻子把备份托付给 beta 软件」。
- 2TB 首备失败/500GB 挂死、暂停后永远无法继续。
- **2026-09 的新证据**：2.4.0.0 stable（2026-09-03）发布后论坛立刻出现「Windows 安装失败丢全部配置」「升级后数据库加密报错」「36 个损坏 filelist 的重建案例」（[Duplicati forum](https://forum.duplicati.com/latest)）——七年老病未愈。

**性能**：海量小文件（默认 100KB 块→单目录海量小对象「弄残 Linux 文件系统工具」）；SQLite 随文件数膨胀；Web UI 慢。

## 6. Rclone（作为备份用途）

**机制**：不是备份工具，是同步引擎：`sync` 单向镜像 + `--backup-dir` 版本化误删保护；`bisync` 双向（仍属「高级命令，用错会丢数据」，需 `--resync` 解锁、>50% 删除即熔断）（[bisync 文档](https://rclone.org/bisync/)）；`crypt` 静态加密层、`chunker` 分块、`check` 哈希校验；70+ 后端。
**无快照、无去重、无索引**——只能做「镜像+备份目录」，历史版本管理原始。定位：restic/borg 的 rclone 桥接后端比直接当备份工具更常见。恢复=文件直接可读（这是它对比所有 CDC 工具的唯一优势：**人类可读的备份布局**）。

## 7. Bacula / BareOS（简述）

企业级 C/S：Director/Storage/File daemon 三组件，全网络集中管理、增量/差分/合成备份、验证作业；Bacula 15.0.3，BareOS 25（AGPLv3 fork）。对个人桌面场景过重，配置复杂（catalog 数据库 + 多守护进程），与 backguard 目标用户几乎不重叠，但其**「备份作业+计划+报告」的集中治理模型**值得借鉴。

## 8. Timeshift（Linux）

已移交 linuxmint/timeshift 维护，最新 25.07.x。定位系统快照（RSYNC+硬链接 或 BTRFS 原生快照），增量、可滚动恢复系统。**不做用户数据备份、无加密、无云后端、无 Windows/macOS**；BTRFS 模式对非 Ubuntu 系发行版有兼容性坑。Linux Mint 预装使其成为「系统还原点」事实标准。

## 10. 市场空白点分析（backguard 机会）

1. **备份不可读/不可理解（哈希海洋）是全行业空白**。所有 CDC 工具的仓库都是内容寻址的随机 pack 文件：Kopia 官方明言「pack 文件名随机、不泄露任何内容」；restic 用户明言「恢复依赖一个能跑的 restic」——**没有一个工具能让普通用户在文件管理器里「看见自己备份了什么」**。机会：仓库内嵌人类可读的 manifest（明文快照清单/README，仅元数据不泄露文件名，机密性可分级），或「导出可读副本」功能。rclone 的镜像可读性是它仍被当备份用的唯一原因。
2. **密钥恢复零工具支持**。所有工具「密码/key 丢=数据全丢」，Borg 官方唯一对策是「把 key 纸质备份放别处」。没有一个产品内建：恢复口令的可验证导出（纸质 QR）、社交恢复门限（Shamir）、或「加密但逃生舱可读」的分层模式。这也是家庭用户最大恐惧。
3. **GUI 全部缺失或半吊子**：restic/borg 官方零 GUI（第三方 Backrest 2026 年才火、被评「UI/UX 怪癖」）；Kopia UI 有但恢复体验翻车案例多；Duplicati 有 UI 但引擎不可靠；Vorta 无 Windows；Pika 仅 Linux。**「三平台 + 官方原生 GUI + 可靠引擎」三要素同时成立的组合不存在**——这是 backguard 最直接的定位洞。
4. **检查/修复与自愈不对称**：restic 无 ECC、无 Object Lock；Borg 靠 `borg check` 手动跑；Kopia 有 ECC 选项但 maintenance 极重（120GB RAM 案例）；Duplicacy 无中心索引导致全量 check 在云上天价。机会：默认轻量持续校验 + 降级自愈 + 勒索防护（Object Lock/版本锁）一体化。
5. **prune/GC 体验糟糕是共性**：restic prune 慢+独占锁、Borg 2.0 为 GC 换库格式、Kopia maintenance 重、Duplicacy fossil 两步删除复杂。机会：无锁后台 GC（Duplicacy 证明了可行性，但它是非开源许可+单人维护——**开源+无锁 GC+可读仓库的组合无人占位**）。
6. **元数据保真没人做全**：Kopia 丢 xattr/SELinux、非 UTF-8 路径存错；跨平台 ACL/ADS(Windows 流)/资源分叉(Finder) 的完整保真+透明展示，是备粉社区长期未满足需求。
7. **信任危机是入口**：Duplicati 的 SQLite 损坏史、Duplicacy 的许可+维护疑虑，把大量用户推向 restic/borg，但后者的 CLI 门槛又劝退普通用户——2026 年这个「可靠但难用 vs 易用但不可靠」的钟摆仍在摆动，没有人同时解决两端。
8. **企业级作业治理 vs 桌面易用断层**：Bacula/BareOS 有作业/计划/报告模型但重到没人愿意在家用；桌面工具又没有「备份是否真的成功、上次可恢复验证是何时」的可信面板。机会：把「恢复演练自动化 + 健康报告」做成默认开启的一等公民。
