## 一、变更检测与增量

### 1.1 mtime/size 快速路径 vs 全量哈希

- rsync 的默认判定即业界基线：`quick check` 算法只比较 size 或 last-modified time；`--checksum` 才切换为全文件 128-bit 校验和比较，且官方明示其代价是 "both sides will expend a lot of disk I/O reading all the data"，会显著变慢（[rsync man](https://man7.org/linux/man-pages/man1/rsync.1.html)）。
- rsync delta 算法只在两端都存在旧版本时才有意义；本地或高带宽场景 rsync 默认 `--whole-file`，说明 delta 传输主要省带宽、不省 CPU/IO，快路径判定永远是元数据。
- 结论性实践：backguard 应实现：本地维护 (path, size, mtime, inode, 上次内容哈希列表) 索引，元数据未变直接跳过读取；mtime 变但 size 未变的高价值文件（数据库）走 CDC 重切比对；提供可配置的周期性全量校验（防 mtime 抚摸攻击/静默损坏，对标 rsync `--checksum` 与 Kopia 的定期 verify）。

### 1.2 文件系统监听做近实时增量：可行性是「平台不对等」

| 平台 | 机制 | 关键性质 | 坑 |
|---|---|---|---|
| macOS | FSEvents | 一个 stream 监视整棵树（传根路径即可）；`latency` 参数批量合并交付；**`sinceWhen` 事件 ID 单调递增且持久化，可回放离线期间的历史事件**；file ID 可跨改名追踪 | 默认只报目录级（需 `kFSEventStreamCreateFlagFileEvents` 到文件级）；`MustRescanSubDirs` flag 出现（卷重挂载等）必须全树重扫；编辑器「临时文件+rename」保存模式使你看到 rename 而非 modify。来源：[Apple FSEvents](https://developer.apple.com/documentation/coreservices/file_system-events) |
| Linux | inotify | 内核级实时 | **非递归**，每个目录一个 watch（大目录树建立 watch 本身就慢）；事件合并（coalescing）使「不可靠计数」；队列溢出丢事件（`IN_Q_OVERFLOW`）；`IN_MOVED_FROM/TO` 靠 cookie 配对 "inherently racy"；不报告 mmap 写入、不支持网络文件系统；上限：`max_user_instances` 默认 128、`max_queued_events` 默认 16384。来源：[inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html) |
| Windows | ReadDirectoryChangesW / **USN Change Journal** | NTFS 卷级持久变更日志，微软明确定位它就是给「自动备份程序」避免全卷扫描、也避免 ReadDirectoryChangesW 必须常驻+大量目录时拖垮系统（[MS Change Journals](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals)） | 日志有 max size/老化，旧记录会被裁剪——裁剪掉的部分必须回退全扫；读 journal 需管理员权限（voidtools Everything 需要管理员服务才能读 MFT+USN） |

- 先例：Everything 用「直接读 MFT（秒级索引百万文件）+ USN 实时增量」实现实时索引，但仅限本地 NTFS、FAT/exFAT 和网络盘退回目录遍历+周期重建。这是 Windows 上增量备份扫描的最优先例。
- 设计共识（三平台通用的容错协议）：FS 监听只能当**加速器**，不能当事实源。任何事件丢失/溢出/coalescing 后都要兜底重扫。架构上应当：
  1. 监听事件 → 合并去抖（如 1–5s 窗口）→ 生成「脏路径集合」；
  2. 备份时优先只扫脏集合，但用周期性全量 walk（如每天/每 7 天）校准；
  3. FSEvents 用 `sinceWhen` 记住水位线；USN 记住 journal ID+USN 水位线；inotify 在 watch 建满前先做一次基线扫描、溢出即降级全扫。
  4. Linux 上更稳的替代：不用 inotify 监视整树，而是周期性并行 stat 对比（fastpath）。主流备份工具（restic/Kopia/Duplicacy）都**没有**做常驻实时监听，均为定时全量元数据扫描 + 内容寻址去重兜底；实时增量是差异化机会，但必须以「提示+校验」模型实现。

### 1.3 快照一致性（备份打开的文件/系统状态）

| 平台 | 机制 | 要点 | 权限/限制 |
|---|---|---|---|
| macOS | APFS 本地快照（`tmutil snapshot`） | 瞬时 COW 快照；可挂载后从快照路径读。Duplicacy 的完整先例流程：检查 APFS+本地盘 → `tmutil snapshot` → 挂载 → 备份 → `umount -f` → 删除快照（[源码](https://github.com/gilbertchen/duplicacy/blob/master/src/duplicacy_shadowcopy_darwin.go)） | 创建快照免 root，但**挂载需要 root**；tmutil 本地快照不支持外置 APFS 盘 |
| Windows | VSS（Volume Shadow Copy Service） | COM 框架，协调应用 writer 与备份 requester，"allows volume backups to be performed while applications on a system continue to write to the volumes"（[MS VSS](https://learn.microsoft.com/en-us/windows/win32/vss/volume-shadow-copy-service-overview)）。restic `--use-fs-snapshot` 每个涉及的卷自动建 VSS 快照；vss.timeout 默认 120s。Kopia 有 VSS policy（`always/when-available/never`，默认 never） | 需要管理员权限；ReFS 不支持持久「以前的版本」式影子副本 |
| Linux | LVM 快照 / btrfs / ZFS 子卷快照 | 均为 COW：瞬时创建、从快照设备/子卷读取保证一致性。btrfs/ZFS 是文件系统原生（`btrfs subvolume snapshot`、`zfs snapshot`） | btrfs/ZFS 需要整卷采用该文件系统（终端用户场景覆盖面小）；LVM 需要 root 且要求 LVM 布局 |
| 通用替代 | 应用级 quiesce / 数据库钩子 | Kopia 的 before/after snapshot actions（pre-backup script，如 `pg_dump`、`sqlite3 .backup`）是不依赖快照的补充手段 | 用户配置 |

**backguard 建议**：三平台快照能力分级——Windows VSS（管理员服务进程，一次授权常驻）> macOS APFS tmutil（root 守护进程或授权 helper 挂载）> Linux（检测 btrfs/ZFS 可用则用，否则退回「运行中备份+重试变化文件」策略）。快照后从只读快照路径扫描，还天然解决「备份期间文件被改导致的数据撕裂」。PBS 的对照：Proxmox 用 QEMU 内部快照机制而完全不依赖存储快照做一致性。

### 1.4 rsync delta vs CDC 去重

- rsync delta（Rollsum 滚动校验和 + 固定块对端匹配）：**两端通信协议**，需要接收端持有旧版本并参与计算，只对「点对点同步一个已知旧版本」有效；对多版本历史去重、多客户端去重、云端对象存储（无计算能力）无效。
- CDC（内容定义分块）：边界由内容决定，插入/删除只影响局部 1–2 个块；块独立按哈希寻址，天然支持任意历史版本、跨机器全局去重、不可变云存储。Duplicacy 白皮书明确对比：固定块每次查哈希表性能差，CDC 滚动哈希只用来找边界，随后用 SHA-256 等强哈希逐块。
- 适用场景：大文件局部修改（VM 磁镜、数据库文件、PST/OST）→ CDC 显著省（PBS 对 VM 磁盘反而用 **fixed 4MiB**：guest 文件系统倾向连续分配，改文件只改自己的块，固定块即足够且零 CPU）。常规文件 → CDC 或文件级整存均可。
- **混合策略是业界共识**（详见 §2.3）。

## 二、CDC 算法细节

### 2.1 滚动哈希家族

- **Rollsum**（rsync 专用）：adler32 变体，基于字节和；最慢且分布一般，仅 rsync 协议在用。
- **Rabin fingerprint**：多项式指纹（restic 在用，window 64 字节，多项式存仓库 config）。乘法型滚动，每字节成本高，是 FastCDC 论文里的「慢基线」。
- **BuzHash**（cyclic polynomial，循环移位异或表）：Kopia（`DYNAMIC-4M-BUZHASH` 为默认）、Duplicacy、PBS（"a variant of Buzhash which is a cyclic polynomial algorithm"）。速度快于 Rabin、实现简单，是「老牌工具」的主流选择。
- **Gear hash + FastCDC**（2016, Xia et al., USENIX ATC）：`h = (h << 1) + G[byte]`（G 为 256 项随机表），每字节一次移位+一次加法，论文报告比 Rabin 基线约 **3 倍**吞吐（综合二手来源称 3–10x）；配套三技术：①normalized chunking（目标点前后用不同长度 mask，块大小分布从几何分布修正为近正态、方差更小）②skip loop（min 之前直接跳过）③simplified hash judgment。2020 年 TPDS 期刊扩展版增加五项技术并给出 **YFastCDC** 等变体；Rust 参考实现（[fastcdc-rs](https://github.com/nlfiedler/fastcdc-rs)）。
- **Borg2 已从 buzhash 转向 FastCDC**（默认 `chunker_params: "fastcdc,19,23,21,2"`）——这是 2024–2026 年新工具选型的风向标：**Gear/FastCDC 系取代 Rabin/BuzHash 是当前趋势**。

### 2.2 主流工具实际参数（源码核实）

| 工具 | 滚动哈希 | min / avg / max | 出处 |
|---|---|---|---|
| restic | Rabin fingerprint（window 64B） | 512 KiB / ~1 MiB（splitmask 20 bits）/ 8 MiB | [restic chunker](https://github.com/restic/chunker/blob/master/chunker.go) |
| Kopia | BuzHash32（默认 `DYNAMIC-4M-BUZHASH`）；可选 RabinKarp64、FIXED-128K…8M | avg/2 / avg / avg*2（即 2M/4M/8M） | [splitter_buzhash32.go](https://github.com/kopia/kopia/blob/master/repo/splitter/splitter_buzhash32.go) |
| Duplicacy | BuzHash | avg/4 / avg / avg*4（默认 avg≈4 MB → 1M/4M/16M） | [duplicacy_chunkmaker.go](https://github.com/gilbertchen/duplicacy/blob/master/src/duplicacy_chunkmaker.go) |
| Borg2 | FastCDC | `fastcdc,19,23,21,2` → min 2^19=512 KiB、max 2^23=8 MiB、mask 21 bits ≈ 平均 2 MiB | [Borg2 frontends.rst](https://github.com/borgbackup/borg/blob/master/docs/internals/frontends.rst) |
| PBS | BuzHash 变体（动态）+ **fixed 4 MiB（VM 磁盘）** | 动态块典型 1–4 MiB 区间 | [PBS technical-overview](https://github.com/proxmox/proxmox-backup/blob/master/docs/technical-overview.rst) |

观察：平均块大小集中在 **1–4 MiB**（块越小去重率越高但元数据/对象数/哈希成本越高；1–4 MiB 是备份场景的平衡点）。min:avg:max 比例约 1:2:4（Kopia、Duplicacy 下限更低 1:4:4——Duplicacy 用更宽的范围换取更好边界稳定性）。

### 2.3 文件级 whole-file + CDC 混合（百万小文件）

- Kopia 的实际做法：**动态阈值**——小于阈值的文件不分块（整文件即一个 content），大文件才 CDC 切块；同时 >2 GiB 的文件启用并行分块上传（`ParallelUploadAboveSize: 2 << 30`，`MaxParallelFileReads` 默认 =NumCPUs）。压缩同理有 MinSize/MaxSize/扩展名黑白名单。
- restic 的做法：所有文件都过 chunker，但小文件本身形成一个 blob，多个 blob 打进 16 MiB pack（上传对象数被 pack 压平）。
- PBS 的做法：小文件（<16MB 配置文件等）走 **BLOB 单对象不切块**，VM 磁盘走 fixed 4 MiB，文件归档走 pxar 流式动态切块。
- 百万小文件的关键成本不在分块而在：①每文件 stat/open/close 系统调用风暴（Linux 上 io_uring 批量 statx / 并行目录遍历可大幅摊薄；Windows 上一个目录内海量条目使 FindFirstFile 枚举退化，Everything 直接读 MFT 是极限方案）②元数据 blob 数量 ③云端对象请求数。对策先例：目录树元数据序列化为树对象（restic tree blob / Borg item / pxar），数据按 pack 合并。
- backguard 建议混合规则：`size < 512KiB`（可调）→ 整文件单块（哈希+压缩+加密后直接入 pack）；`512KiB–4MiB` → CDC；已知大文件类型（vmdk/vhdx/qcow2/数据库/视频已压缩）→ 跳过 CDC 用 fixed 4 MiB 或 no-CDC 直传。

## 三、存储/传输性能

### 3.1 压缩

- zstd 官方基准（i7-9700K，Silesia）：zstd -1 = 2.896 压缩比 @ **510 MB/s 压缩 / 1550 MB/s 解压**；lz4 = 2.101 @ 675/3850 MB/s；zlib -1 = 2.743 @ 105/390 MB/s。解压速度与等级基本无关（[zstd](https://facebook.github.io/zstd/)）。
- 工具默认：restic v2 仓库 `--compression off/fastest/auto/better/max`，默认 **auto**；Kopia 数据默认 **none**、元数据默认 **zstd-fastest**；Borg 默认 **lz4**；Kopia 基准表：s2-default 4 GiB/s（压缩比最差）、zstd-fastest 356 MiB/s、zstd-best 19.2 MiB/s。
- **按块压缩，不按流压缩**（restic/Borg/Kopia/PBS 一致）：块级独立压缩使随机恢复单文件无需顺序解压整流，代价是失去跨块上下文（zstd `--long` 可补但与按块加密冲突）。Kopia 官方原则可直接采用："只要压缩吞吐超过 I/O 速度，压缩就不再是瓶颈，更高等级相当于免费"；并且**压缩后变大时自动回存原始数据**（Kopia 已实现）。
- 顺序铁律：**先压缩后加密**（密文高熵不可压缩）。PBS 更进一步：加密块的哈希按「明文+密钥」计算，因此命中去重的块**根本不需要加密**，只有真正要上传的块才加密——这个设计直接省掉重复块的加密 CPU，值得照抄。
- backguard 建议：默认 zstd-3（速度与比平衡点，接近 500 MB/s 单线程，多核下远超磁盘吞吐）；提供 zstd-1（电池模式）/ zstd-19（归档模式）；已压缩扩展名黑名单跳过；按块独立压缩 + 「压缩变大回退原文」。

### 3.2 打包（pack）与上传

- restic pack：16 MiB 目标大小（`--pack-size` 可调，TiB 级仓库/快速上行链路建议加大），data/tree blob 混合分 pack，pack 尾部加密 header 列出各 blob 偏移——索引只需读 header，且 blob 可独立加密认证使 pack 可重组而不必重加密。注意代价：临时空间 = pack size × (connections+1)，64 MiB pack × 5 连接 ≥ 384 MiB 临时盘占用（且加大 pack 增加 SSD 写损耗）。
- Borg 1.x 用 append-only **segment 事务日志**；**Borg2（2025–2026）已改为 restic 式 pack + 独立 index**（`packs/00..ff/` 一级哈希前缀目录、`index/` 存 chunk→pack 位置、store hash 用 BLAKE3）。两大阵营格式趋同 = pack 模型已被验证为最优。
- PBS chunk store：chunk 文件按**哈希前 4 个 hex（0000–ffff）预建目录**分桶，"to reduce the number of files per directory, as having many files per directory can be bad for file system performance"。
- 上传并发：restic 后端连接数默认 5（本地 2），官方提醒过高连接数反而降速；Kopia 并行读 =NumCPUs、>2GiB 文件并行分块；`RESTIC_READ_CONCURRENCY` 调 NVMe 读并发。
- S3 约束（对 pack 大小的硬约束）：part 5 MiB–5 GiB、最多 10000 parts、单对象上限 **48.8 TiB**、官方建议 ≥100 MB 对象走 multipart。**小文件合并上传对云端的意义**：S3/多数对象存储按请求数+存储量双重计费，百万 4KiB 小对象 = 百万 PUT 请求 + 百万 List 开销 + 计费对象数；打包成 16–64 MiB pack 可将请求数压缩 4 个数量级，这也是 restic/Kopia/Borg 全部采用 pack 的根本原因。云端断点续传：pack 级幂等（pack 名=内容哈希，失败重传即可）+ S3 multipart 分 part 断点续传。
- backguard 建议：目标 pack 32 MiB（默认）可调 16–256 MiB；pack 内部分 section 对齐 multipart part（8 MiB/section），上传中即可逐 section 并发 PUT；本地暂存用环形缓冲限制临时盘占用（避免 restic 的 384 MiB 问题）。

### 3.3 本地缓存/索引与冷启动

- restic：本地 cache 目录按仓库 ID 隔离，缓存 index/data(tree)/snapshots，LRU 按目录 mtime 过期。
- Kopia：本地持久化**全量 content 索引**（content ID→blob 位置），冷启动免下载；blob 缓存 + **epoch manager** 将索引组织为按时间分代的 blob 组（epoch 按数量/大小阈值推进）——解决多客户端并发写索引的冲突与索引 blob 数量增长。
- 扫描器性能：restic 提供 `--no-scan` 关闭预估统计（对网络盘/FUSE 有收益，说明扫描统计本身有可观 IO 成本）；Linux 可用 io_uring 批量 statx/开放目录枚举摊薄 syscall；Windows 的 Everything（MFT 直读+USN）证明 NTFS 上目录树枚举可以被数量级加速，但需管理员权限。
- backguard 建议：本地 SQLite/自有 KV 存三层缓存——①路径→元数据（增量扫描）②content ID→pack 位置（去重判定，免联网）③最近 pack 的 blob 缓存（恢复加速）。冷启动首备=全量扫描不可避免，用并行遍历（每核一个 worker + 目录级 work steal）+ 批量 stat；Windows 可选管理员服务读 USN 维护实时索引。

### 3.4 GC/合并

- restic prune 痛点与改进（官方 0.12.0 release notes）："prune is now much faster…especially for remote repositories"；改进包括：基于既有 index 而非从零重建、repack 步骤并行处理 pack、snapshot 内容扫描并行化数倍提速。可调项：`--max-unused` 默认 **5%**（容忍的废数据上限，越低 repack 越多）、`--max-repack-size`、`--repack-cacheable-only`（只 repack 元数据 pack，极快）、`--repack-smaller-than`（合并小 pack）。prune 期间仓库加锁、备份被阻塞——需错峰调度。
- Kopia：maintenance 分 **quick（默认 ~1h，控制 q/n 类 blob 数量保性能）与 full（默认 24h，mark-and-sweep snapshot GC + blob compaction）**；独占 owner 锁；因对象存储最终一致性，"full maintenance 的效果不是立即的"，依赖时间推移保证安全。epoch manager 自动做索引分代合并。
- Duplicacy：无索引 GC，两步 fossil collection（先改名隔离→确认无新引用再删），支持多客户端无锁并发。
- backguard 建议：在线式增量 compaction（Kopia 式定期 blob compaction）优于 restic 式重锁全量 prune；GC 用 mark-and-sweep + 安全窗口（CleanupSafetyMargin 先例）；小 pack 合并常态化而非集中式大整理。

## 四、恢复性能

- 并行恢复：Kopia `kopia restore --parallel` 默认 **8**，并有 `--write-sparse-files`（稀疏写出，最小化磁盘占用）。restic 0.17.0 重构 restore：pack 改大块下载而非流式（防中断失败）、blob 级重试。
- 稀疏文件：按块压缩/按块加密天然支持稀疏恢复——全零块在压缩后极小，恢复端检测全零块用 `fallocate(FALLOC_FL_PUNCH_HOLE)/seek` 稀疏写。数据库镜像、VM 磁盘恢复受益最大。
- 挂载浏览：restic mount 仅支持 **Linux/macOS/FreeBSD，不支持 Windows**；macOS 依赖 FUSE-T 或 macFUSE；且官方明示「恢复大量文件时 restic restore 比 mount 显著更快」，mount 适合取少量文件/检视。Windows 侧 WinFsp 提供 FUSE 兼容层（原生支持 FUSE API，"In many scenarios it performs as well as NTFS"，GPLv3+FLOSS 例外许可）——但 restic 至今未接，说明 Windows FUSE 恢复路径工程成本不低。
- backguard 建议：restore 主路径 = 并行 worker（默认 min(8, cores)）+ 预取 pack 索引 + 稀疏写 + 断点续传（已完成文件跳过）；mount 作为可选组件（Linux/macFUSE/WinFsp 三套后端）不进 MVP。

## 五、资源占用设计

- 网络/IO 限速：restic 全局 `--limit-upload/--limit-download`（KiB/s，默认不限）。
- CPU：restic 用满核，`GOMAXPROCS` 限制；读并发独立可调（NVMe 加大）。
- 后台优先级：
  - Linux：`nice` + `ionice -c3`（idle class）是事实标准；cgroup v2 `io.max`/`cpu.max` 限速更精确（systemd 服务 `IOSchedulingClass=idle`）。
  - macOS：Time Machine 的 backupd 以**低 I/O 优先级**运行（内核 IOPOL_THROTTLE 层级）；Low Power Mode 下后台备份被显著拖慢/暂停，电池低电量时 Time Machine 延迟备份、接电恢复。工程手段：`setiopolicy_np(IOPOL_UTILITY/IOPOL_THROTTLE)`、QoS `NSBackgroundActivityScheduler`、`taskpolicy -c utility`。
  - Windows：进程优先级 `BELOW_NORMAL_PRIORITY_CLASS`/`IDLE_PRIORITY_CLASS`；备份进程避开前台窗口（`SetProcessInformation` 的 PROCESS_POWER_THROTTLING）；VSS 快照创建本身有 120s 超时上限的先例。
- 对前台的影响控制：PBS/restic 均把「从快照/只读视图读」与「限并发读」作为主手段；Kopia 把并行度（快照数、文件读数）作为 policy 而非全局参数，可以按目录粒度降级。
- backguard 建议：统一的 resource governor——四维（CPU 核数、IO 带宽、网络带宽、并发句柄）+ 三档模式（用户活跃/空闲/电池/低电量），用电量/电源状态事件驱动自动切换（接电升档、低电量暂停、系统空闲检测升档）；所有备份 IO 走后台优先级标记。

## 六、backguard 性能架构建议

流水线：**检测 → 快照 → 扫描 → 分块 → 压缩 → 加密 → 打包 → 上传**，每级可并行、可背压（bounded channel），本地索引贯通全链路。

```
[水位线增量源]                    [数据面]
 macOS: FSEvents(sinceWhen)      扫描(并行目录遍历+批量stat, io_uring/Linux)
 Win:   USN Journal(水位)   ──►  快照视图(VSS/APFS/btrfs, 只读路径)
 Linux: 周期walk+inotify(脏提示)      │
        ▲ 事件丢失兜底: 周期全量校准    ▼
        │            mtime+size+inode 快速路径(本地索引未变→跳过读)
        │                     │ 变化文件
        │                     ▼
        │       ┌─ <512KiB: whole-file 单块（Kopia/Duplicacy 先例）
        │       ├─ 512KiB–: FastCDC 切块（Gear hash, avg 1MiB 可调至 4MiB）
        │       └─ VM磁盘/已知类型: fixed 4MiB（PBS 先例）或 no-CDC 直传
        │                     ▼
        │       BLAKE3/SHA-256 哈希(明文) ──► 本地 content 索引查询
        │                     │ 未命中才继续（命中块零后续成本, PBS 先例）
        │                     ▼
        │       zstd-3 按块压缩（黑名单跳过/变大回退, Kopia 先例）
        │                     ▼
        │       AES-256-GCM 按块加密（先压缩后加密）
        │                     ▼
        │       pack 打包（目标 32MiB, 8MiB section, restic/Borg2 先例）
        │                     ▼
        │       并发上传（连接池 4–8, S3 multipart 续传, 限速器）
        ▼
[GC] mark-and-sweep + blob compaction（quick 1h / full 24h, Kopia 先例）
```

各环节业界先例与参数建议：

| 环节 | 建议参数 | 先例 |
|---|---|---|
| 增量检测 | 元数据快速路径（size+mtime+inode）；FSEvents sinceWhen 水位 / USN 水位 / inotify 仅作脏提示，周期全扫校准 | rsync quick check；FSEvents/USN；主流备份工具均以定时扫描+去重兜底 |
| 快照 | Windows VSS（管理服务，timeout 120s）；macOS tmutil（root helper 挂载后 umount+删除）；Linux btrfs/ZFS 原生、否则跳过 | restic `--use-fs-snapshot`；Kopia VSS policy；Duplicacy darwin shadow copy；PBS |
| 分块 | FastCDC（Gear hash），默认 min 512KiB / avg 1MiB / max 8MiB，归档模式 avg 4MiB；<512KiB 整存；VM 磁盘 fixed 4MiB | Borg2 `fastcdc,19,23,21,2`；restic 512K/1M/8M；Kopia buzhash 2M/4M/8M；Duplicacy 1M/4M/16M；PBS fixed 4M |
| 哈希 | BLAKE3（索引/块 ID，速度优势）；或 SHA-256 兼容生态 | Borg2 store hash=BLAKE3；restic/Kopia/PBS=SHA-256 |
| 压缩 | zstd 按块，默认 level 3；fast=1 / archive=19；黑名单+回退 | Kopia s2/zstd 表、Borg lz4 默认、restic auto |
| 加密 | 先压缩后加密；AEAD per chunk（AES-256-GCM / ChaCha20-Poly1305）；明文哈希寻址（重复块免加密） | restic AES-CTR+Poly1305；Kopia AES-GCM；PBS 明文+key 哈希 |
| 打包 | pack 32 MiB 目标（16–256 可调），pack 内 8 MiB section 对齐 multipart；本地暂存环形缓冲 ≤ pack×2 | restic 16 MiB 默认+S3 5 MiB part 下限；Borg2 pack |
| 上传 | 连接池 4–8（过高反降速）；pack 级幂等重试；限速器全局 | restic connections=5；S3 multipart |
| 索引 | 本地三缓存（路径元数据 / content→pack / blob cache）；多客户端 epoch 分代合并 | Kopia 索引+epoch manager；restic cache |
| GC | 在线 compaction：quick（每 1h，控小 blob 数）+ full（每 24h，mark-sweep，安全窗口） | Kopia maintenance；restic 0.12+ prune（max-unused 5%） |
| 恢复 | 并行 worker（默认 8）+ 稀疏写 + pack 大块下载 + 断点续传 | Kopia `--parallel=8 --write-sparse-files`；restic 0.17 大块下载 |
| 资源 | 四维限速（CPU/IO/网络/句柄）+ 电源感知（电池降档/低电量暂停）+ 三平台后台优先级 | restic --limit-*；Time Machine；macOS QoS |

**核心结论**（供决策）：① CDC 用 FastCDC/Gear（Borg2 已改投，性能 3–10x 于 Rabin），平均块 1–4 MiB、min/avg/max=1:2:4；② pack 文件模型是 restic/Kopia/Borg2 三方收敛的终局答案，云端请求数/成本压平 4 个数量级；③ 快照能力决定产品档次（VSS/APFS 是必须项），FS 监听只做加速器、水位线+周期校准兜底；④ 顺序固定为 哈希(明文)→压缩→加密→打包，命中去重的块零压缩零加密（PBS 先例）；⑤ GC 用 Kopia 式在线分代 compaction 而非 restic 式全局锁 prune；⑥ 资源治理做成电源感知的统一 governor 是对笔记本用户体验的最大差异化。
