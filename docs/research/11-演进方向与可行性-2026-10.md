# 11 · 演进方向与可行性评估（2026-10-01）

> 输入：[10 章](10-现状复核与竞品增量-2026-10.md) 的实测现状 + 三路竞品调研
> （个人备份 GUI 层 / 可验证性与企业路线 / 消费级网盘生态）+ [07 章](07-产品定位与竞争优势.md) 原路线。
> 输出：一份**按当前事实约束重排**的演进清单，每条都给最小可验证形态与红线检查。

## 0. 评估的前提（先把事实边界钉住，否则路线是从想象推的）

| 事实 | 对演进的含义 |
|---|---|
| 真实设备 **1 台**（particloud-macos）、真实云端 **1 个**（123Pan WebDAV 单账号） | 3-2-1 里的「2」和「1」目前都不成立，这是**最大单点**，比任何新功能都优先 |
| 用户 **1 个**（作者本人），无外部反馈 | 「是否需要 GUI」没有证据；任何界面投入都是自嗨 |
| 观察期（2026-09-30 起，14 周），代码迭代降速 | 大改（引擎、格式、目录形状）代价 = 观察数据作废 |
| 一轮 CI 85–110 分钟（macOS 池排队），部署靠 ff 部署树 | 每个改动的验证成本以「半天」计，方案必须能**攒批** |
| 已有 9 条 shell E2E + 49 单测 + 6 CI runs + 「新断言必须变异验证」的规矩 | 新功能只有在**能挂上守卫**时才值得做——否则它是负债 |

一句话：这个阶段的产品问题不是「功能不够」，是**证据不够**（证据 = 别人/未来的你能验证它真的能恢复）。

## 1. 四个恐惧 × 现状打分

竞品调研把用户对备份的不信任收敛为四条：静默停摆、恢复失败、内容不明、密钥丢失。

| 恐惧 | backguard 现状 | 缺口 |
|---|---|---|
| 静默停摆 | ntfy 成功回执（刚修好泄漏） | **只证「跑成功」，不证「该跑时跑了」**——真机 `never exited` 就是活样本 |
| 恢复失败 | drill 抽样真实取回（7 PASS）+ rescue.sh + restore.md | 比对只看 **size**；restore.md 里有条会真解包的错命令 |
| 内容不明 | 明文 MANIFEST/STORY/COVERAGE + 加密 ledger | 叙事基线被 prune 冻住，连读 7 天讲同一件事 |
| 密钥丢失 | age 双路径（identity + 恢复码）、口令已轮换 | 密钥**第二副本仍是纸质**（设计决定），无异地加密副本 |

## 2. 演进候选（按「单位投入换多少可信度」排，不按酷的程度排）

每条给：解决什么 / 最小可验证形态 / 成本 / 是否撞红线。

### A 组：观察期内就该做（各 ≤ 半天，且都能挂守卫）

**A1 恢复指南的正确性守卫**（修 §10 缺陷 1）
- 做什么：`restore.md` 模板里 `borg extract --list` 改 `borg list --short`；解包示例明确「先 `cd` 进目标目录」。
- 最小验证：E2E 断言明文产物不出现 `extract --list`；再在夹具里**照产物文本执行一遍**（产物即脚本，能跑通才算指南）。
- 红线：不触碰隐私/凭据；这是恢复面的正确性，属于必须。

**A2 恢复校验补上「内容」这一维**（现状：`semantic/semantic.sh:387` 只比 `file_size`）
- 实测约束（10-01 现问现验）：borg 1.4 的 `list --format '{sha256}'` **取不到每文件哈希**
  （rc=0 但值为空——borg 只对 chunk 做内容寻址，不对文件），所以「备份期顺手记哈希」这条
  在 macOS/Linux 侧需要自己多读一遍源文件；restic 侧 `ls --json` 本来就带哈希，不用付这个成本。
- 于是分两步做，别一步到位：
  - **A2a（便宜，引擎自带，先做）**：月度跑 `borg check --verify-data`（config 仓库 73 MB，分钟级）
    与 restic `check --read-data-subset`。它证明「存储没腐化、能解密解压缩」，
    但**不证明取回路径可用**——那仍是 drill 的职责，两者不互相替代。
  - **A2b（中等，按需）**：ledger 里对 ≤N MB 的文件记 sha256（绝大多数小文件/配置被覆盖），
    drill 命中就比内容、没记就退回比 size 并在结论里**如实标注是哪种依据**。
- 最小验证：夹具造「同长度不同内容」的文件（正好是 123Pan 只比大小那课的镜像），
  断言 drill 报错；A2a 则断言 rc 与告警可见。
- 理由：企业侧 SureBackup 与开源 `restore --verify` 都停在取回级；业界口号 3-2-1-1-0
  的末位「0」就是这个位置。

**A3 双证人可观测：外部心跳（dead-man's switch）**
- 做什么：备份结束时向一个 expected-key 的 URL PUT 一次（healthchecks.io 式）；**没跑就没有 ping，超时即告警**。与 ntfy 回执互补，不替代。
- 最小验证：E2E 桩切网断言失败不影响备份（非致命分层）；URL/token 按凭据纪律只进 `secrets.env`，日志与回执一律不落 token。
- 为什么值得：这是唯一能覆盖「排程没触发/机器没醒/进程卡死」的机制，而这类事故在日志里**永远是空的**。
- 口径依据（竞品调研）：healthchecks.io 官方哲学就是「按时到达则沉默、缺失即告警」，
  专杀漏排程/卡死/静默崩溃，但它**分不清「跑完了但内容错了」**；ntfy 官方文档自己写明
  topic 是公开的、要选不可猜的名字（与我们这次「回执落日志=topic 泄漏」事故互证）。
  所以两者是**互补的两个证人**：心跳管「该跑有没有跑」，回执+drill 管「跑了的结果对不对」。
  Prometheus 生态对批任务的标准姿势是 Pushgateway 推短生命周期指标，但 restic/borg 的
  官方级 exporter **未查到**——个人场景用 Pushgateway 是过度工程。

**A4 运行史可审计：日志轮转 + run 边界行**
- 做什么：每轮写一行 `run 边界：<时间> sha=<部署树短 SHA> rc=<n> dur=<s>`；超阈值轮转（保留 N 天）。
- 最小验证：E2E 跑两轮断言出现两条边界行且旧日志被轮转。
- 收益实证：今天因为日志里混着已修的历史错误，代理误判现役缺陷花了 10 分钟——未来的自己和用户都会遇到同一件事。

**A5 叙事基线口径分离**（修 §10 缺陷 2）
- 做什么：STORY 的「相比」改用**上一份快照**（本地 `runs/run-*.json` 留 60 份，够用），并单独一行说明「引擎侧最近可回到的归档 = X（prune 之后）」。
- 最小验证：夹具造「同一天两次备份 + 中间被 prune」的形状，断言基线是上一次运行而不是被裁后的祖父。
- 红线检查：只改渲染，明文层不新增任何文件名，隐私不变式仍由现有单测锁。

**A6 云端可信副本的定期自证（10 章 §5.5 那条结论的落点）**
- 为什么单列：现在「云端有副本」的全部证据是 `rclone copy` 的退出码，而 10-01 已经实测到
  这条 remote 上比较退化成**只比大小**——原地同长度重写永远推不上云，copy 照样报成功。
  也就是说退出码**不是**「云端有新版」的证据，它只是「rclone 没报错」的证据。
- 分层做，把提取流量当成预算来花（现役网盘 2025-11-26 起免费额度从 60 GB 砍到 10 GB/月，
  超额 0.05 元/GB；我们仓库 7.6 GB，整仓拉一次几乎吃光当月额度）：
  - **L1 清单级（每轮备份后，零提取流量）**：`rclone lsl` 拿云端对象数与逐对象 size，
    与本地 ledger 对平；对象数减少、size 与本地不一致 → 非零退出并告警。
    这能抓住「没上去」「少了一份」「云端被改动」，抓不住「同长度不同内容」。
  - **L2 内容级（月度，预算内）**：对明文时间轴（实测 ~69 MB）逐文件 `rclone cat | shasum`
    对比本地，加三类仓库各自的 `config`（几百字节，key blob 就在里面——换口令后云端是否
    有新版就靠它）。合计 <100 MB，额度风险可忽略。
  - **L3 真解包（人工，季度）**：在**另一台机器/另一个系统盘**上用 `rescue.sh` 从云端做一次
    盲恢复。它花的不是额度而是时间，也是 §4「一次真实恢复耗时」的同一次动作。
- 结论去向：写进时间轴明文（`CLOUD-VERIFY.txt`，只记对象计数、字节数、哈希前缀与判定，
  不记文件名——隐私不变式沿用），并推 ntfy 回执；**失败不阻断备份**（非致命分层）。
- 最小验证：夹具把云端副本改一个字节 / 删一个对象，断言 L1 或 L2 报错且结论行是 FAIL；
  变异时把 `sha` 比对那行摘掉，确认断言真的咬不住（不是一句永远为真的 echo）。
- 与 NAS 厂商的差距表述：群晖/威联通做到的是「源-目标哈希比对 + 自己的日志」，
  A6 做的是同一件事但**结果不需要它的软件就能读**——这是 10 章 §5.4 认定的差异化位置。

### B 组：条件触发（有第二台设备 / 观察期结束时）

**B1 第二副本（把 3-2-1 做真）**
- 做什么：`BACKUP_TARGETS` 已是数组、`sync_target` 已支持多目标 → 接第二目标（外置盘挂载点 或 第二个 rclone remote）几乎是配置活；需要补的是**第二个目标失败时的可见性**与「只增不减」在本地盘上的等价规则。
- 风险：网盘账号是唯一云端，服务条款/降速/封号任一发生就归零（第三路调研的核心结论）。
- 最小验证：`test_multi_target.sh` 扩展为「一目标成功一目标失败」，断言退出码非零且不宣布 FULLY COMPLETE（现有红线已覆盖一半）。

**B2 Windows 补齐**（#20）
- 做什么：`semantic.ps1` 的本地时间轴保留策略（现在无界增长）、`rescue.ps1`、以及把 CI 的 `Assert semantic timeline` 从自认的弱守卫改成真锁形状。
- 前置：**本机无 pwsh**，所以只能靠 CI 的 windows job 做变异验证（推一个故意错的分支看它红不红）——成本一轮 CI，可接受。
- 为什么在 B：T1.6 dogfood 扩 Windows/Linux 各一台之前必须完成，否则新设备一上就带着已知缺口跑。

**B3 多设备聚合视图**
- 做什么：timeline 根级 `profile.json` 已经在，缺的是「跨设备的当日汇总」（今天 3 台里哪台没跑）。
- 为什么不是 A：只有 1 台真机时它是想象；有 2 台以上才是需求，且那时需求会非常硬。

### C 组：明确**不做**（并写下什么条件下改主意）

| 不做 | 理由 | 改主意的前提 |
|---|---|---|
| 自研引擎（FastCDC/pack/分代 GC） | 04 章的最优解全部公开，但「重写一个 restic」的成本是人数年；而 restic/borg 已经是用户信任的对象，换引擎不增加任何**证据** | 出现引擎层面的硬阻塞（如 WebDAV 上 restic 的锁模型不可靠到不能自动恢复） |
| 官方云托管 | 客服/合规/密钥托管争议是运营成本，单人项目承担不起；BYO + rclone 长尾已覆盖 | 有 ≥20 个非作者用户在用 |
| 原生 GUI（时间轴浏览/健康徽章） | CCC 靠「副本可直读」、Arq 靠「格式公开」建立信任，**没有一家靠界面**；反例是群晖 Hyper Backup——它有完整 GUI 与校验日志，但**验证结果只有它自己的软件读得懂**，且官方明说「备份数据库损坏就救不回任何备份」。我们的明文层已经站在这一列的对立面 | 有真实用户抱怨命令行不可用 |
| Shamir 分片 / 硬件密钥 stanza / PQ 包裹 | 03 章的远期项，成本在**维持**（旧 stanza 永久可解）；当前恢复码 + 双 X25519 已覆盖主要风险 | 出现因单一恢复路径失败而丢数据的实例 |

## 3. 重排后的阶段划分（对 07 章的一处修正）

07 章：Phase 0 语义层 → Phase 1 GUI + 官方云 → Phase 2 自研引擎 → Phase 3 信任纵深。
本章建议：**Phase 1 = 信任纵深（A 组 + B1），Phase 2 = 多设备与跨平台补齐（B2/B3），
界面与云托管推迟到出现外部用户之后**。

理由三条：
1. 竞品在「可验证性」上的公共短板（机器校验有、人可读证据无）我们已经天然占位，
   **加固它比开新战场便宜**；
2. 现状复核（10 章）跑出的四条缺陷全在信任面，不在功能面；
3. 单设备单网盘的风险结构意味着「备份存在」这件事目前仍系于一个账号的存续，
   这比任何新特性都更接近致命。

## 4. 观察期该盯的数（不新增代码也能得到的证据）

- nightly **连续成功天数**（今晚是新一代代码的第一次夜跑）；
- drill 通过率与抽样覆盖类别（config/files/system 各命中）；
- 云端对象数**单调不减**（任何减少都是事故，`rclone size` 每日一条）；
- 「一次真实恢复耗时」：随便挑一天，按 `restore.md` 的字面指令恢复一个文件，
  计时并记录是否需要额外知识——这是语义层唯一诚实的验收方式。

## 5. 第二目标选型（B1 的具体决策，事实来自 10 章 §5）

现状：**一个消费级网盘账号是唯一的异地副本**。三条候选路的代价各不相同，先把它们摆平：

| 候选 | 挡住什么 | 挡不住什么 | 我们的实际约束 |
|---|---|---|---|
| 外置盘 / NAS（家用同址） | 主机盘坏、误删、勒索（只要不挂载） | 火灾/盗窃/同时烧掉主机与盘 | 已有一部分：`~/PartiverseBackup` 就是本地事实源，再加一块同址盘只是「本地 + 1」，不构成 3-2-1 的第三个位置 |
| 第二个消费级网盘 | 单一服务方改规则致零 | WebDAV 语义不完整的同一课要重学一遍；两家国产网盘的风控先例是**同类**风险 | 便宜、零流量费；但「多一个账号」不是「多一类风险模型」 |
| 对象存储（B2 / R2 / Wasabi / 阿里 OSS） | 服务方政策、异地、版本控制/对象锁可选 | 按请求/流量计费的账单模型；**AK/SK 泄露的爆炸半径**（一对密钥能一次删光云端） | B2 $6.95/TB/月、R2 恢复零出口费（05 章结论）；7.6 GB 目前 ≈ **$0.05/月**，成本可忽略 |

结论（可执行顺序，不是「都想做」）：

1. **B2/R2 作第三副本**是这里唯一能同时满足「异地 + 语义正确（原生 S3 有 modtime 与 ETag，
   不会再掉进只比大小的坑）+ 成本 < 一杯咖啡」的选项；接它的前提是
   **开版本控制或 Object Lock，并把 AK/SK 限定为只写不能删的子密钥**——否则只是把
   「一个账号能被封」换成「一对密钥能被泄」。
2. 网盘账号继续作**主存**（体量决定：0.05 元/GB 的提取费只在恢复日才疼，
   而恢复是低频事件），但把 10 章 §5.1 的额度条款读进 `COVERAGE`/文档，
   让「恢复一次要花多少钱」是已知数而不是恢复当天的惊吓。
3. 同址外置盘只在「需要秒级恢复一个误删文件」时才有价值，属于体验层，不是容灾层；
   在只有 1 台设备时**不做**。

触发条件：观察期结束（≥2 周连续 nightly 绿）且 T1.6 第二台设备上线之前——
那时「跨设备聚合」和「第三副本」会同时变成硬需求，先做后者。

## 9. 10-02 实测补录：时间轴的重量 99.9% 是密封清单，压缩比 19.1×（未动代码，待拍板）

预演当晚（`run 边界: sha=5abbf68 rc=0 dur=84s`）顺手把「时间轴到底多重、重量在哪」量了一遍，
因为这直接决定 A6 L2 的流量与每晚 WebDAV 推送的成本：

| 口径 | 实测 |
|---|---|
| `~/PartiverseBackup/timeline` 总量 | 107 MB |
| 其中 `manifest.json.enc`（12 份） | **106.3 MB（99.3%）** |
| 其中全部明文语义产物（62 个文件：MANIFEST/STORY/COVERAGE/restore/CLOUD-VERIFY/INTEGRITY/profile.json） | **0.07 MB** |
| 云端 `Backguard:particloud-macos/timeline` | 71 objects / 106.4 MiB（云端只增不减，同一形状） |
| 单份密封前的 `manifest.json` | 3,351,578 B |
| `gzip -9` 之后 | 175,586 B（**-6 是 180,656 B**）→ **19.1×** |
| A2a 整仓逐块解密校验 | config 0s / files 24s / system 1s（7.6 GiB ≈ 25s） |

三条结论：

1. **语义层的成本全在「密封」这一侧**，不在明文渲染那一侧。明文层是 KB 级的，密封清单是 MB 级的，
   而它每天一份、云端永不删除 ⇒ 每晚固定涨 ~3.4 MB（10-01 那批设备状态大时是 ~11 MB/份）。
   在密封前加一层 gzip（`age(gzip(json))`）可把它压到 ~0.18 MB/晚，**顺带把 A6 L2 的月度全量
   哈希流量同比例砍掉**——L2 之所以今天要读 106 MB，几乎全是在读重复的文件名列表。
2. **这是密封格式变更，不是性能微调**：`manifest.json.enc` 的形状同时被三处消费——
   `seal_manifest`（备份期写）、`run_drill`（演练期解封取样本清单）、`rescue.sh`（盲恢复期解封列文件）。
   已上云的 10 份旧 enc **必须仍可解**，所以兼容做法与「时间轴去设备层」同一套：解封侧先试
   gunzip、失败退回原样（两种形状都认），而不是加开关或迁移历史。按 §2 的规矩，
   这类格式/命名体系变更要用户拍板后才动，观察期内不自作主张。
3. 另一条更省的路（**不建议**）：密封清单不逐份全量存，只存最新一份 + 增量。它省得更多，
   但破坏「每个快照自带它那一份名单」的恢复语义——`rescue.sh` 的卖点正是「拿到一个日期就能列出
   那天有什么」，增量链一旦断一环，中间那些日期的名单就永久不可得。体积问题用压缩解决，
   语义问题不要拿来换体积。

**A2a 成本被这次实测改写了**：roadmap 原文按「分钟级」估计整仓校验，实测 7.6 GiB 只要 25 秒，
所以「月度整仓读一遍」的代价几乎可以忽略——它也因此变成 L2（逐文件内容核对）最便宜的参照系：
本地读一遍仓库 25 秒，而云端读一遍时间轴要按 106 MB 的提取流量算。
