## 二、复核跑出来的四条真缺陷

1. **`restore.md` 教了一条会真解包的命令**。`semantic/bg_semantic.py:643` 渲染
   `borg extract --list <仓库路径>::<归档名> <子路径>`。borg 1.4 的 `extract --list`
   **不是只列表**——它顺带报告路径但实际解包到 cwd（AGENTS §2 已记这条引擎事实，
   `rescue.sh:372` 的注释也知道清单走 stderr，唯独面向「干净机器上的人」的产物模板漏了）。
   这份文件存在的全部理由就是「没有这个软件时照着做」，所以它的错误代价 = 恢复者在
   仓库目录里意外落下一棵全量文件。
   守卫口径：断言任何明文产物里不出现 `extract --list`，列路径只许 `borg list --short`。

2. **STORY 的叙事基线会「冻住」**，真机 9 份快照实测：

   ```
   2147-evening  →（首份，无基线）
   0948-morning  → 相比 2026-09-29 21:47
   0134 / 0234 / 0241 / 0303 / 0440 / 0935 / 1019（10-01 的 7 份）→ 全部「相比 2026-09-30 09:48」
   ```

   原因不在渲染器：基线取的是**引擎里还活着的上一个归档**，而 borg prune 的 keep-daily
   把 10-01 当天 7 个归档裁成 1 个（files 仓库现仅 4 个归档）。于是时间轴上连读 7 天
   都在跟同一个基线比，「新增 26 · 修改 195」重复 7 遍。
   这是**口径问题**而非 bug：用户读时间轴期待「上一次备份」，代码给的是「上一个未被裁的归档」。

3. **日志没有轮转**：`backup.log` 1088 行，头部 6 行是 init.sh 修「include 单字符串格式」
   **之前**那次的 `✗ [include 路径] …不存在`，而第 1002/1003 行（最近一次）是
   `preflight: 全部检查通过 / 0 个错误`。历史错误与现役状态混在一个文件、无运行边界标记，
   今天实际把代理误导了一次（把已修问题当现役缺陷排查了 10 分钟）。

4. **可观测性有单证盲区**：ntfy 只在「跑成功」时说话。真机现状是 launchd 装载后
   **从未退出过**（`never exited`），若某天排程根本没触发，用户侧没有任何信号——
   这正是竞品调研里 dead-man's switch 专杀的场景（见 §三.3）。

## 三、竞品增量（相对 01/02/07 章的 2026-09 版本）

### 1. 「可读性」这条差异化有先例可引，但位置仍是空的
- **Carbon Copy Cloner**（官方）：恢复件挂载即用文件管理器直读、完全绕开应用——
  与 backguard 明文层同源，是最有力的对标先例（证明「不依赖软件的副本」在消费级成立）。
- **Arq**（官方）：宣称备份文件格式「publicly auditable」，用**格式公开**回答
  「恢复出来是什么」；但没有叙事、没有干净机器自助恢复文档。
- 开源组（Vorta / Pika / Duplicati / Kopia）全部把内容锁在引擎私有格式里，
  「归档列表 + 选文件恢复」是及格线，我们靠明文层直接越过这条线。
- 结论：07 章「语义化仓库全行业空白」的判断**依旧成立**，且现在有了可引用的邻近先例
  （CCC / Arq），叙事更硬而非更弱。

### 2. 「我能恢复吗」：机器校验有人做，**人可读的校验证据没人做**
- Duplicati 有可计划化的完整性校验（读回全部块做哈希核对）；Kopia 有
  `snapshot verify`（官方明说它 stops short of downloading/decrypting blobs，需抽样百分比）；
  borg `check --verify-data` / restic `check --read-data` 同理停在「仓库完整」。
- 真正到「取回级」的只有 restic `restore --verify` 与抽样解包——**正是 drill 的位置**。
- 企业侧 Veeam SureBackup 与我们的 drill 同构（自动执行 → 判定 → 留档报告），
  差距只在验证级别：企业开机跑脚本证明「应用级可用」，个人场景的最小升级是
  **把取回比对从 size 升到内容 hash**，并把连续通过率当作审计指标。
- 「不验证等于没备份」在业界已收敛成口号 **3-2-1-1-0**（末位 0 = 零错误/已验证）。

### 3. 告警：回执推送与外部心跳是**互补**不是替代
- healthchecks.io 官方哲学：pings 按时到达就沉默，**缺失即告警**——专杀漏排程/卡死/静默崩溃，
  但无法区分「跑完了但内容错了」；ntfy 主动回执相反，能带成功内容却不会在「没跑」时说话。
- ntfy 官方文档自己写明 topic names are public、要选不可猜的名字——与本次
  「回执 JSON 落进日志 = topic 泄漏」事故互证，凭据纪律那条口径是对的。

### 4. 「讲故事」在备份产品里无先例
- `git log/diff` 证明「每次变更有叙事」在版本控制里是基建；备份侧 restic/borg 的 diff
  只是 CLI 瞬时输出，不落盘、不给非专家读。Time Machine 是消费端唯一把「时间轴回看」
  做成核心体验的，但它不产出任何「这次备份讲了什么」的文档。
- **未查到任何备份产品持久产出人话叙事文档**——STORY.md 仍是无先例定位。

### 6. 企业「恢复证明」的同构物与差距（第二路调研，来源以官方文档为主）
- **Veeam SureBackup**（官方）：直接从备份归档在隔离沙箱自动开机 → 跑预置测试 +
  自定义验证脚本 → 产出**可审计的恢复性报告**，定位就是 "guarantee recoverability"；
  Dell Avamar 有"按需备份验证"；Cohesity REDLab 用沙箱重放勒索家族检验可恢复（厂商研究，二手）。
  **backguard 的 drill 与 SureBackup 同构**（自动执行 → 判定 → 留档报告），差距只在验证级别。
- **群晖 Hyper Backup**（官方文档）是消费级里最接近我们的一件事：可勾选
  **"Verify Data Integrity"** 做**哈希级**校验、能**检测静默数据损坏**、
  且每次校验写入**有版本记录的审计日志**（报告里逐条显示验证结果）。
  但它同时暴露一个反面教材：**备份数据库一旦损坏就救不回任何备份**（官方原文警告）。
- 开源引擎自己的验证面**三家都停在「仓库完整」**：borg `check`（默认 CRC/结构，
  `--verify-data` 才全量解密解压）、restic `check --read-data[-subset]`（`restore --verify`
  才是取回级）、kopia `snapshot verify` 官方明说 "stops short of downloading, decrypting,
  and decompressing the blobs"。**真正证明「取回可用」的只有抽样解包——正是 drill 的位置。**
- 业界口径已收敛为 **3-2-1-1-0**（末位 0 = 零错误/已验证，QNAP/NinjaOne/AvePoint 方案页）；
  「不验证等于没备份」在 r/Backup 是共识（论坛印象）。
- 结论：backguard 的 **drill + 明文时间轴在个人市场无直接先例**，且与企业趋势同频。
  差异化最硬的一句话是：**Hyper Backup 能验证，但要它自己的软件才读得懂验证结果；
  我们的结论（`rescue-test.txt`）与内容清单（明文层）在裸文件管理器里就可读。**
  而它的「DB 损坏即全丢」正好反衬我们把可读产物**复制上云、只增不减**这一步的价值。

### 5. 待补的一节：消费级网盘作为备份目标的风险
（由并行的第三路调研补入：WebDAV 语义不完整、只比大小、账号与政策风险、
以及「唯一云端」应该配什么缓解手段。）

### 5.1 现役目标（123 云盘）已经在**恢复面**上收费并点名风控
- 2025-11-26 官方《免费用户权益调整通知》：全渠道每月**提取流量**由约 60GB 降到 **10GB**
  （官方客户端 20GB），超额 **0.05 元/GB 且不足 10GB 按 10GB 扣**，取消游客免登录下载 <100MB；
  官方明说此举为封堵**「爬虫软件批量抓取或高频下载」**、抵制绕过接口的自动化工具与挂载
  （[转载官方通知](https://www.laoliang.net/news/27693.html)、
  [新浪/17173 报道](https://news.17173.com/content/11272025/200419457.shtml)）。
- 对本项目的直接含义：**我们那个 7.6 GB 仓库真要恢复一次，几乎吃光当月免费额度**；
  而备份工具最讽刺的失败就是「恢复时才发现取不回来」。
  `verify_cloud`（逐文件 `rclone cat`）今天跑一次 53 个对象 ≈ 89 MB，是额度的 0.9%，
  但**全量仓库校验**（borg `check --verify-data` 若指向云端副本）就不只是慢，而是花钱。
- 123 有官方开放平台但 API 需申请审核（[123pan.com/developer](https://www.123pan.com/developer)），
  社区 300GB 实测称其 WebDAV 不稳定（[bilibili 实测](https://www.bilibili.com/video/BV1ZJ4m1773n/)），
  AList 侧对应 issue [#3006 无法下载](https://github.com/AlistGo/alist/issues/3006)、
  [#7417 大文件上传失败](https://github.com/AlistGo/alist/issues/7417)、
  [#7282 每日下载额度](https://github.com/alist-org/alist/issues/7282)（维护者原话：改了官方会针对性再改）。

### 5.2 「只比大小」不是我们的猜测，是 WebDAV 的官方事实
rclone 官方 WebDAV 后端文档写明 **"Plain WebDAV does not support modified times" /
"plain WebDAV does not support hashes"**（[rclone.org/webdav](https://rclone.org/webdav/)），
目录 rename/move 不可用是论坛长期问题（[rclone 论坛](https://forum.rclone.org/t/unable-to-rename-and-move-directories-via-webdav/22341)）。
→ 我们的「同长度原地重写推不上云、而 copy 报成功」这条实测教训有官方依据，
`test_remote_caps.sh` 能力台账应当把「比较依据是 size 还是 hash」作为**接入必查项**长期保留。

### 5.3 国产网盘生态的整体风险结构（政策单向变更有先例）
- **阿里云盘**：2023-02 封第三方 WebDAV 挂载 → 2024-04 再限 → 2024-07 起
  **「三方应用权益包」10 元/月 / 110 元/年**才换官方 WebDAV（[IT之家](https://www.ithome.com/0/782/707.htm)、
  [landiannews](https://www.landiannews.com/archives/97273.html)）——14 个月内政策三次收紧。
- **115 网盘**：**API 开放平台 2026-08 全面暂停**，并有会员因迁移操作被封号
  （[115 官方帖](https://115.com/115/T977462.html)）——「开放」可以随时收回。
- **百度网盘**：无官方 WebDAV，第三方接入历史上大规模封号（[转载](https://m.163.com/dy/article/D8KMIH8H0511AGD9.html)）；
  **夸克**：无官方 WebDAV/API，全靠逆向只读桥接（[quarkdrive-webdav](https://libraries.io/cargo/quarkdrive-webdav/1.2.9)）。
- **坚果云**：**唯一官方完整 WebDAV**（应用密码制），但免费版单文件 500MB、
  请求 **600 次/30 分钟**（付费 1500）、**PROPFIND 单次最多 750 项需分页**
  （[官方帮助](https://help.jianguoyun.com/?p=2064)）——时间轴那种深目录树会直接撞这两条闸。
- 桥接层：**AList** AGPL-3.0、50.2k stars、2025-06 起有「被收购/部分功能收费闭源」的社区报道
  （未经官方证实），社区因此分了 **OpenList**（AGPL-3.0）；**CloudDrive2 闭源商业**，
  免费版限 2 个云盘（[定价页](https://www.clouddrive2.com/pricing.html)）。
  → 把 AList 当依赖要注意 **AGPL 的传染性**与「上游随时变脸」这两条。

### 5.4 NAS 厂商把「可验证性」做到了哪一步（对位我们 drill 的最硬证据）
- **群晖 Hyper Backup**（官方规格）：完整性检查「数据与索引」用于**检测历史版本损坏**、
  客户端 AES-256 + ECC Curve25519、**最多 65,535 版本 + 自定义轮转**、S3 目标支持
  **WORM WriteOnce 不可变保留**，并有 Hyper Backup Explorer 让用户浏览备份内容
  （[官方功能页](https://www.synology.cn/zh-cn/dsm/feature/hyper_backup)、
  [技术规格](https://www.synology.com/en-global/dsm/7.2/software_spec/hyper_backup)）。
  但官方同页警告：**备份数据库一旦损坏就救不回任何备份**。
- **威联通 HBS 3**（官方教程）：数据完整性检查分两级——基础比对**存在性/大小/mtime**，
  高级用 **MD5 内容校验**，可按排程对备份集执行、检出损坏后**自动尝试修复**；
  其 3-2-1-1-0 方案页把「可验证恢复」做成**把每份备份自动放进沙箱开机** + Instant Restore
  （[HBS3 完整性检查](https://www.qnap.com.cn/zh-cn/how-to/tutorial/article/hbs-3-%E4%B8%AD%E7%9A%84%E6%95%B0%E6%8D%AE%E5%AE%8C%E6%95%B4%E6%80%A7%E6%A3%80%E6%9F%A5)、
  [3-2-1-1-0](https://www.qnap.com.cn/zh-cn/solution/3-2-1-1-0-rule)）。
- **两家的共同上限**：校验 = 源-目标比对 + 哈希，**不做真实抽样恢复**；
  而 backguard 的 drill 是真取回、结论还落在**不需要任何软件就能读**的明文层。
  这就是差异化的准确表述——不是「别人没做校验」，而是
  **「别人做了校验，但校验既不解包、结果也只有它自己的软件读得懂」**。

### 5.5 三句话风险结论（第三路调研原文）
1. 把消费级网盘当**唯一**云端，最致命的是**服务方单方面改规则**（115/阿里/123 都有先例），
   叠加 WebDAV 语义不完整，备份可能**静默失效而无人察觉**。
2. NAS/外置盘作第二目标，首要限制是**同址性**——不与主机异地就挡不住火灾/盗窃/勒索。
3. 对象存储作第二目标，首要限制是**按请求/流量计费的账单模型**与
   **AK/SK 泄露的爆炸半径**（一对密钥可以一次删光云端，必须开版本控制/保留策略）。

> 两条调研给出的同一结论：**如果只能做一件事，就是把「云端有可信副本」从
> `rclone copy` 的退出码，变成按计划、非人工、对着云端内容做哈希并留档告警的一次真取回。**
> 这恰好是 5.4 里 NAS 厂商做到 80% 的那一环，也是我们唯一能自证「网盘没骗我」的手段。
> （可行性见 [11 章 A6](11-演进方向与可行性-2026-10.md)）

## 四、对 07 章路线的一处修正建议（理由见 11 章）

07 章写于代码落地前，隐含前提是「一个要做成产品的团队」，因此排了
Phase 1 GUI + 官方云、Phase 2 自研引擎。当前事实是：**单人 dogfood、一台真机、
一个消费级网盘账号、观察期**。按这个事实重排优先级，结论会把「自研引擎」与
「官方云」从路线图里**移出**，把「可验证性纵深 + 第二副本 + 双证人告警」提前。
