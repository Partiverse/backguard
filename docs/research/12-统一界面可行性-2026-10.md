# 12 · 统一界面（备份管理 UI）可行性 — 2026-10-03

> 调研性质文档，**不含实现**。两份并行子 agent 报告（本仓内部盘点 + 外部竞品）汇总而成。
> 内部盘点的原始表格见 §2，外部证据逐条给来源链接。结论与推荐在 §1、§5。
>
> 前置约束：AGENTS.md §1 四条红线（明文层隐私 / 凭据纪律 / 非致命分层 / 云端只增不减）
> 与 §1.5「不可逆操作先确认」在本篇里是**设计输入**，不是待商榷项。

## 1. 结论（一句话 + 三条推论）

**今天不做界面；如果做，只做「本地只读状态页」这一档，且它的价值八成来自一个还没有的地基
产物（每轮一行的结构化状态 JSON），而不是来自界面本身。**

- 推论 1：界面在本项目的真实需求是**状态可见性**（昨晚成没成、云端有没有可信副本）与
  **恢复可信度**（演练/完整性结果），**不是**「在界面上点恢复」。后者在竞品里是主界面，
  在 backguard 里正面撞 §1.1（见 §3）。
- 推论 2：`verify-nightly.sh` 已经是「只读重算今晚状态」的雏形（它不写任何东西、只打
  pass/fail 计数）。把它的判据落成一份结构化产物，收益比先画页面大得多——那份产物同时
  服务 CLI、通知、和将来的任何一种壳。
- 推论 3：桌面 App / Electron / Web 框架是**第四轨**。本仓第三方依赖目前为零（全仓无
  pip/requirements/package 痕迹），而 §3 的验证纪律（新生产面 → shellcheck + CI + 变异）
  会把每次界面改动定价为半天起，与观察期降速节奏相反。

## 2. 内部盘点：今天有什么可读、有什么可做

### 2.1 数据源（按机器可读度排）

| 源 | 位置 | 可读度 | 界面可用性约束 |
|---|---|---|---|
| run JSON | `$LOG_DIR/runs/run-YYYYMMDD-HHMMSS.json`（bash 写 `semantic.sh:350`，留 60 份 `:182`；Win 侧 `semantic.ps1:410,557`） | 完全可解析，`format=backguard/semantic-run/1` | **内含全量文件名**（真机单份 22 MB），只许本地读、渲染层须重做收敛 |
| 快照四件套 | `timeline/YYYY/MM/DD/HHMM-标签/{MANIFEST,STORY,restore,COVERAGE}` | 纯文本给人读 | 已经是「界面」，只是静态 |
| `INTEGRITY.txt` / `CLOUD-VERIFY.txt` | timeline 根 | 半结构化，逐行状态 + 汇总行可 grep | 差异样本只到目录，已合规 |
| `profile.json` | timeline 根 | JSON | 设备身份，无敏感名 |
| `preflight-latest.json` | `$LOG_DIR` | JSON `{errors,warnings,findings[]}` | **message 含绝对路径**（`bg_semantic.py:1085`） |
| run 边界行 | `backup.log` 每轮一行 `sha= rc= dur=`（ps1 侧 ASCII `run boundary:`） | 单行可解析 | **最便宜的「当晚成败」索引** |
| `rescue-test.txt` | 只留本地 | 逐条文本 | **带完整文件名**（§1.1 唯一例外），天然不可外传 |

### 2.2 动作入口与危险分级

- 立刻备份：`backup.sh` / `backup.ps1 -Task Backup`。非破坏（云端只增），但与 nightly 并发会撞
  引擎锁（borg rc=2 / restic rc=11）；真机一轮 84 s、CI 6–13 min ⇒ 界面须处理长任务与锁竞争。
- 恢复：`restore.sh --list` 只读安全；`--latest/--id --target` **写文件＝不可逆**（§1.5 确认门）。
  `rescue.sh --list/--find/--ledger/--guide` 只读，`--get --to` 写；`rescue.ps1` 同构。
- 演练：`drill.sh --force` 绕 30 天节流，解包进临时目录、不动用户树 ⇒ 相对安全，但读 secrets.env，
  并发持锁会把 nightly 的完整性记成 UNKNOWN。
- 改保留策略：**引擎侧今天做不到**——7d/4w/6m 硬编码在 `backup.sh:130,185`、`backup.ps1:146`，
  不是配置项。可配置的只有 `SEM_TIMELINE_KEEP` / `SEM_RUN_JSON_KEEP` / `SEM_LOG_KEEP` / `INTEGRITY_DAYS`。
  ⇒ 任何「在界面上调保留策略」的设想都**先是一次配置面改造**，不是 UI 活。

## 3. 红线对界面的硬约束（为什么不能照抄竞品）

§1.1 明文层隐私的适用范围原文包括「**任何新写的、会随时间轴上云的明文产物同受这条约束，
包括机器报告**」。推到一个界面上：

1. **呈现即泄漏**。最结构化、最想渲染的两个源（run.json 全量文件名、preflight 绝对路径）恰是
   禁外传的那两个。界面把本地 0600 的信息渲染成可截图、可分享、可缓存的形态，等于自动升级了
   它的传播等级。§1.2 明确「不进 issue/截图」——**截图本身算泄漏面**。
2. 绝不出现的：完整文件名、口令/恢复码、**ntfy topic（topic＝订阅密码）**、上云产物里的绝对路径。
   `INTEGRITY.txt` 为此连引擎原文都不抄（引擎的锁错误行带仓库绝对路径）。
3. §1.4 云端只增不减 ⇒ 界面**不得**提供「云端删除/同步」类动作。
4. §1.5 ⇒ 恢复、覆盖、改配置全部走确认门；§1.3（非致命分层）意味着界面后端崩了不能影响备份本体，
   所以它只能是**旁路读**，不能成为备份链路上的任何一环。

竞品里有一面镜子：`borg-webgui` 的 README 自己承认处理不了访问控制，而「浏览快照」等于把全部
文件名与尺寸摊给每个能打开该页面的人（[repo](https://github.com/mshopf/borg-webgui)）。这正是 §1.1
要挡的那一档。

### 4.2 商业薄壳暴露什么

Arq（[站](https://www.arqbackup.com/)）、**CCC**（[bombich.com](https://bombich.com/)：任务面板显示下次
运行/最近结果、Snapshot Browser 按文件名搜历史、三级校验 + 定期 Backup Health Check、任务日志记录
目标端变化）、Time Machine（[时间轴 + 逐项恢复](https://support.apple.com/en-sg/guide/mac-help/restore-items-backed-up-with-time-machine-mh11422/10.13/mac/10.13)）、
Synology Hyper Backup（[向导配计划/轮转/加密，恢复走浏览旧版本](https://kb.synology.cn/zh-cn/DSM/tutorial/How_to_browse_and_restore_Hyper_Backup_backup_data_in_hbk_file_format)）、
Acronis（恢复点浏览 + 单文件恢复）。

**共性**：界面＝**状态 / 调度 / 恢复**三件；口令轮换、仓库修复、精细调优一律留 CLI 或高级页。
**BorgBase（SaaS）的边界最硬**：只管配额与告警，**不能浏览归档、不能改计划、不能解密、不能远端恢复**，
恢复一律回客户端（[borgbase](https://www.borgbase.com/)）——一家靠 borg 吃饭的公司把界面收在这里，
是「解密与展示分离」的成熟判断。

### 4.3 两条与本项目直接相关的行业判断

1. **「界面核心是恢复」是反复出现的一手口径**：borg-webgui 作者原话是别的 UI 只管备份那一侧，
   而恢复才是唯一面向普通用户的动作；新项目 Backhome（[repo](https://github.com/soccervortex/backhome)）
   把卖点写成 dead-simple restore，调度/保留反而标 Planned。**但这一档在 backguard 里恰好是
   §1.1 挡下的那一档**（浏览快照＝摊文件名）。我们的对应物是 `rescue.sh --guide`：它把「怎么取回」
   讲清楚而不替人解密展示全量名单。
2. **「今晚发生了什么」作叙述式界面——未找到任何先例**。最接近的四类是快照 diff 列表
   （snapper/`restic diff`，机器名单不是叙述）、每晚统计邮件（borgbackupserver、Backrest 通知）、
   时间轴导航（Time Machine、Genie Timeline）、CCC 的任务日志。也就是说 STORY.md 这一层在竞品里
   **没有对应物**：是差异化，也是无验证风险（没人替你证明这个形态有人用）。

## 5. 选项与推荐

| 选项 | 内容 | 成本 | 与红线 | 判断 |
|---|---|---|---|---|
| **A0 不做** | 维持现状：STORY/MANIFEST/COVERAGE + ntfy 通知 + `verify-nightly.sh` | 0 | 无新增 | 观察期的默认，且**不失任何现有能力** |
| **A1 状态地基**（推荐先做这一发） | 每轮落一份**紧凑状态 JSON**：engine rc/dur、cloud-verify 状态、integrity 汇总、drill `n/N`。只含计数与状态、**零文件名、零绝对路径** | 小（一个渲染点 + 一份守卫 + 变异） | 天然合规：判据与 `INTEGRITY.txt` 同源 | **界面价值八成在这里**；CLI/通知/任何壳/未来的页面都是它的读者 |
| **A2 本地只读页** | stdlib `http.server` 绑 127.0.0.1，只渲染 A1 的 JSON + 三份文本报告尾巴；无写操作 | 中（新增第三轨生产面 → shellcheck/CI/变异全套） | 只要不渲染 run.json 原始内容就合规 | 有存活先例（Backrest 路线），但**先问有没有人要** |
| **B 桌面 App（Electron/Tauri/PyQt）** | 全功能 GUI | 高（每平台打包签名 + 双份维护；Kopia 就是 release 资产翻倍那例） | 恢复浏览那页与 §1.1 正面冲突 | **不做** |
| **C 集中管理（多设备面板）** | agent 轮询 + 服务器 | 高（borgbackupserver 那类要缓存明文目录树） | 与 §1.1/§1.2 冲突最尖锐 | **不做**，除非产品定位改成设备管理 |
| **D 配置向导** | 首装时把 config.sh/secrets.env/age/调度问一遍 | 中 | 凭据录入面＝新增泄漏面 | 现有 `init.sh` 已覆盖主要场景，收益不明确 |

**推荐路径**：A0 → A1 立刻可做（它与「做不做界面」这个决策解耦，是纯收益）→ 拿 A1 跑 1–2 周
真实观察期，若人真的开始问「能不能有个地方看一眼」，再上 A2；**B/C 明确排除**。

## 6. 若继续，需要用户拍板的四件事（设计闸门）

1. 界面要不要有**写操作**（立刻备份 / 触发演练 / 恢复）？只要有，就要处理引擎锁竞争与 §1.5 确认门，
   成本从「一个只读页」跳到「一个新的生产面入口」。**建议：A2 阶段只读，写操作一律回 CLI。**
2. 保留策略（7d/4w/6m）是否配置化？这是**产品决策**，与界面无关，但界面上「可改」的预期会倒逼它。
3. 目标受众：只有你自己（particloud-macos + 未来 2 台设备），还是要给非技术用户？后者才需要 B 档，
   而 B 档与 §1.1 的冲突无法在实现层解决。
4. 呈现深度：允许出现哪些标识？建议白名单口径沿用 §1.1——一级目录名 + 计数 + 状态 + 时间，
   并**显式声明**「本页面永不渲染 `runs/*.json` 与 `preflight-latest.json` 的原始内容」。

## 7. 风险登记（Top 3）

1. **呈现即泄漏**：界面价值与 §1.1 收敛深度直接冲突，且截图是合法外传路径。缓解＝A1 那种
   「零文件名」的地基产物，而不是渲染层加过滤。
2. **验证成本**：新生产面 ⇒ §3 全套纪律（变异 + 挂 CI）。CI 一轮 85–110 min、macOS 排队，
   界面改动的反馈环比 CLI 慢一个数量级。
3. **动作天花板**：最该有的动作（改保留策略、仓库修复）今天**没有可点的入口**（硬编码），
   界面只能做「看」和「跑现成脚本」；一个只能看静态报告的页面，与已经存在的 STORY.md 相比
   增量有限——这是 A2 相对 A1 收益薄的根本原因。
