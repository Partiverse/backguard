## 1. 项目一页纸

**Partiverse Backup（仓库名 backguard）**：三平台（Linux/macOS/Windows）个人备份系统。
在成熟引擎（borg/restic）与 rclone 之上做两层增值：

1. **语义层**（「看得懂的备份」，全行业空白一）：每次备份自动生成裸文件管理器可读的
   `MANIFEST.txt`（明文摘要卡）、`STORY.md`（中文叙事 + 断档 >48h 置顶警示）、
   `restore.md`（本快照恢复指引）、`COVERAGE.txt`（「什么没被备份」明示 + 排除规则变更告知）；
   完整文件名单独密封进 age 加密的 `manifest.json.enc`。
2. **强制恢复码体系**（全行业空白二）：age 双 X25519 recipient（主身份 + 恢复码包裹的
   救援身份），`bg drill` 周期抽样真实取回文件验证恢复链路。

**当前阶段**：Phase 0 验证期（14 周计划 2026-10 → 2027-01）的**观察期起点**。
核心功能面已全部落地并在一台真实设备实战运行；代码迭代降速，重心是被动观察与 dogfood。
战略背景与全部调研依据在本地 `research/` 8 章 + `PRD.md`（见 §2）。

### 4.7 ntfy 回执把 topic 写进了日志（10-01 午后，凭据纪律的另一面）

`notify_push` 原来是 `curl -sS … "$SEM_NTFY_URL" >>"$LOG" 2>&1`——把 HTTP 响应**连同 stderr 一起
追加进 `backup.log`**。公共 `ntfy.sh` 的回执是 JSON，里面有 `"topic"` 字段，而**topic 名就是订阅
密码**（§1.2 明写「口令不进日志」，但当时没人把响应体当凭据看）。真机 `backup.log` 里确实躺着
整份回执，所以：旧 topic 作废、换成新随机 topic（只落 `config.sh`，600），日志里的旧值全文替换为
占位符，**用户需按新 `SEM_NTFY_URL` 重新订阅**。

- **修法**：`curl -fs -m 10 -o /dev/null … >/dev/null 2>&1`——`-f` 让 4xx/5xx 走非零退出进
  「推送失败」分支，`-o /dev/null` 把 body 关在 curl 内部，stdout/stderr 一律丢弃。诊断只剩
  「成 / 不成」两态，这正是排查需要的全部信息量。
- **守卫**（`test_cloud_failure.sh` 新增）：stub curl 除记录调用外，**按真服务那样**吐回执 JSON
  到 stdout、吐 `curl: (22) …` 到 stderr，退出码由 `CURL_STUB_RC` 控制。第 3 轮让推送本身失败，
  断言①走「推送失败」分支、②备份退出码仍为 0（§1.3 非致命分层）、③扫描运行日志 + 配置目录 +
  明文时间轴 + 测试自身两份 stdout，`e2e-topic` 必须零命中。两个防空转反向断言：`curl.log`
  （测试自己的调用记录，不算日志面）里确有 topic，且第 2 轮确有「已推送」。
- **变异验证**：把 `semantic.sh` 还原成 `>>"$LOG" 2>&1` 的树 → `E2E-FAIL: ntfy 回执里的 topic
  落进了日志`，命中文件就是 `…/partiverse-backup/backup.log`（失败原因与被测面一致，不是旁路崩）。
- **四条自伤教训（都记进 AGENTS §2 的口径）**：① 生成 stub 的 heredoc 没加引号，
  `exit ${CURL_STUB_RC:-0}` 在**写桩那一刻**就展开成常量 `0`，第 3 轮改环境变量永远切不动——
  桩里的变量必须 `\$` 转义；② 新增轮次会覆写 `out.log`，前一轮的「已推送」证据得先 `cp` 存成
  `out.round2.log`，否则新断言把旧断言踩死；③ `X="$(find … | head -1)"` 在 `set -euo pipefail`
  下会被 head 提前收工引发的 SIGPIPE（rc=141）炸掉赋值，加 `|| true`；④ 新断言的失败文案里写了
  `rc=$rc，`——**本机 bash 5.3.20 跑 `test_cloud_failure.sh` 全绿，是 `test_portable_stat.sh`
  的静态扫描点名拦下的**（§2 那条只在 3.2 与 homebrew 5.3.15 上才炸）。这条反过来正是守卫的价值：
  别拿本机行为当保证，跨 locale 的坑由扫描器兜。

### 4.10 缺陷 5：STORY 的「相比」用错了基线（10-01 傍晚，roadmap A5 落地）

- **现象**：`build_story` 的「这次备份相比 X」和 >48h 断档提醒都读 `parent_time`，
  而 `parent_time` 是**引擎里上一份还活着的归档**（`prev_archive_for` 从 `borg list` 取），
  不是用户心里那句「上一次备份」。`borg prune` 把当天的多次备份裁成一份以后，两者能差
  一天以上——增量数字于是**冻住重复**（同一份「新增 N 张」连着出现好几天），读起来像
  这几天什么都没发生。
- **真正严重的是告警方向**：断档提醒按 `parent_time` 算，保留策略裁掉中间归档就会
  **凭空造出一条「距上次备份已约 4 天，请留意定时任务是否正常」**——而昨晚明明跑成功了。
  伪告警比漏告警更糟：观察期靠这类提示建立信任，第一次假警报就是把这条通道废掉。
- **改法**（口径分开，不做取舍）：`run.json` 新增 `prev_run_time` = **时间轴上的上一份快照**，
  由 `semantic.sh` 从 `$stage` 的深度 4 目录名（`YYYY/MM/DD/HHMM-标签`）解析后以
  `--prev-run-time` 传入；`build_story` 在两者相差 >90 s 时补一行「口径说明」引用（说明增量
  是跨中间几次备份的合计），断档改按 `prev_run_time` 衡量、缺失才回退 `parent_time`，
  MANIFEST 卡片优先写「上一次备份」。90 s 阈值是给同轮多类别之间那几秒抖动留的余量，
  否则每次正常夜间备份都会被贴一条无意义的说明。
- **退化面**：老 `run.json`、以及还没接这条参数的 Windows `semantic.ps1`（§6 小项 1）拿不到
  `prev_run_time`，STORY 就退回单口径渲染，不报错、不空行。**时间轴形状不认识时整段不传**
  （正则守卫 `^[0-9]{4}$` + `^[0-9]{4}-`），迁移遗留的旧形状目录最多让说明行消失，不会传进
  一个错误时间。`prev_run_time` 不早于本次快照的一律不认——`SEM_TIME` 可以被覆盖（demo/补录），
  那种情况下时间轴里最后一份其实「在未来」，写出来会变成「上一次备份在明天」。
- **守卫**：2 条单测 / 4 个判定点（双口径分列、一致时不打扰、缺参数退化、断档不被 prune 伪造），
  单测总数 49→51；
  `test_restore_e2e.sh` 断言 7 用真机同形的时间轴（种子 `2026/10/02/0234-night`、`SEM_TIME` 设成
  10-03、fixture 的 parent 归档是 09-29）一次卡住 STORY 两行、MANIFEST 卡片行，并断言
  **不得出现「断档」**。变异 4 条逐个咬住：摘 bash 接线 / `gap_src` 改回 `parent_t` /
  MANIFEST 分支退回引擎口径 / `prev_run_time()` 恒返回 None。

### 4.11 缺陷 6：现役日志里混着早已修掉的历史错误（10-01 傍晚，roadmap A4 落地）

- **现象（自己踩的）**：§4.9 那次复核在 `backup.log` 里读到 09-30 的 rclone 500，按现役缺陷
  排查了十分钟才确认它不再复发。读日志的人——包括下一次会话里的代理自己——没有别的途径
  知道「这一行属于哪一轮、那一轮的部署点是什么代码」。
- **改法**（`backup.sh`，两件都在 main 里 LOG 定稿之后接）：
  1. **日志轮转** `rotate_log_if_oversized`：超 `SEM_LOG_MAX_BYTES`（默认 4 MiB）才 `mv` 成
     `backup.log.<YYYYmmdd-HHMMSS>` 副本，再按 mtime 留最近 `SEM_LOG_KEEP`（默认 7）份。
     轮转列表**点名四份**（`backup/rclone/sem/drill.log`）：`launchd.*.log` 由 launchd 持有句柄，
     切了它等于把后续输出写进已 unlink 的 inode；`runs/` 与 `system-meta/` 各有自己的保留策略。
     `LOG` 若被 config 指到 `LOG_DIR` 之外，只打一行说明并跳过轮转（权限归一化照做）。
  2. **run 边界行** `log_run_boundary`（EXIT trap，`trap 'log_run_boundary "$?"' EXIT`）：
     一轮一行 `[时间] run 边界: sha=<部署树短 SHA> rc=<n> dur=<s>s`。sha 取
     `git -C "$SCRIPT_DIR" rev-parse --short HEAD`，取不到就写 `nogit`（退化不是错误）；
     写失败 `|| true`——边界行属于旁路，没有资格让备份非零退出。
- **删除面是这段代码唯一真正危险的地方**（宽 glob `"$f".*` 会捞到用户手放的 `backup.log.bak`、
  同名目录），所以两道守卫串在 `rm -f` 前：形态正则 `^<base>\.[0-9]{8}-[0-9]{6}$` +
  必须是普通文件（`rm -f` 对目录是 rc=1，main 正常路径上 set -e 会把整次备份带走）。
  逐行 `read -r` 消费候选，不做 `ls | xargs rm`（AGENTS §3）。
- **踩到的新坑：`ls -1t "$f".*` 对目录操作数打印的是**目录内容**，不是目录名本身**。
  少了 `-d`，同名目录从候选清单里**根本不存在**——于是「挡住目录」那道守卫等于没被测到，
  变异 4（摘掉 `[[ -f "$g" ]]`）当时**E2E 照样全绿**。加 `-d` 后它当场咬住。两个 bug 还会
  互相掩盖：不加 `-d` 时 ls 给目录内容加路径前缀（`20240101-000000/a.txt`），形态守卫把它
  挡在删除之外，看起来像「守卫在起作用」。
- **另一处取证口径**：`info/warn` 只写 stdout（`backup.sh:14-17`），`$LOG` 里只有引擎
  `tee -a` 进来的输出和边界行。所以断言「跳过告警真的运作过」要取夹具的 `out.log`，
  取 `backup.log` 会断言到一个恒为假的字符串上。
- **守卫**：`test_log_rotation.sh`（新，四阶段真机同形）——超阈值恰好切一次且历史噪音离开
  现役日志 / 未超阈值不得再切 / `SEM_LOG_KEEP` 封顶且保留的是最新的三份（种子 mtime 全部
  `touch -t` 写死，否则同秒并列让「留哪几份」变成运气）/ 非轮转形态与同名目录都必须活着 /
  失败轮（只读仓库根）的边界行 `rc=[1-9]` 如实。已挂 CI（linux + macos 各一步，E2E 由九条增至十条）。
  **6 条变异逐个咬住**：摘轮转调用 / 摘 EXIT trap / KEEP 不封顶 / 摘普通文件守卫 / 摘形态守卫 /
  把 `ls -1dt` 改回 `ls -1t`。
- **门禁**：51 单测 + shellcheck 0 告警（`backup.sh` 五文件清单）+ `test_portable_stat.sh`
  的变量紧贴非 ASCII 静态守卫（本轮抓到并修掉 `backup.sh` 两处、新 E2E 两处 `$rc）`/`$LOG）`）
  + 本条 E2E 与其余九条全 PASS。

### 4.12 缺陷 7 的对策：云端可信副本每轮自证（10-01 夜，roadmap A6 L1 落地）

> §4.9 的缺陷清单里，「rclone 在这条 remote 上只比大小」是**唯一一条会影响备份可信度**的：
> 换口令后 `config` 从 700 B 变 700 B，nightly 报「同步完成」，云端三个 `config` 全是轮换前
> 那份（AGENTS §2 WebDAV 段）。当时是靠人手工对平发现的。A6 L1 把它变成每晚自动发现并自动修。
> 判据与额度预算见本地 `research/11` §A6；L2（每月把明文时间轴 `rclone cat | shasum` 全量核
> 一遍，约 69 MB 流量）与 L3（异机盲恢复）留作后续。**这一条不是从零开始**：10-01 上午手工
> `rclone copy -I … --include config` 把三个 `config` 推平过一次（§4.4），A6 L1 是把那套手工
> 动作变成每晚自动，从此不必有人在。

- **零提取流量的两条判据**（`backup.sh` 的 `run_cloud_verify`，只在推送全报成功之后跑）：
  1. **清单单向包含**：`find` 本地树 → `path\tsize`，`rclone lsl` 云端 → 同一形状，`comm`/`join`
     比对。本地有的云端必须有且同尺寸；**云端多出来的一律不计失败**——那是 borg prune /
     `SEM_TIMELINE_KEEP` 裁掉的历史，云端只增不减是设计（红线 §1.4）。写成双向相等就每晚假报。
     两类不一致分开计数并报缺失样本（「缺 N 个 / 尺寸不符 M 个」+ 前三个路径），否则失败了
     也分不清是哪种、该补传谁。
  2. **仓库 `config` 的内容哈希**：`rclone cat <dest>/<类>/config | sha256` 对本地同算法。
     这一条才是「只比大小」的克星——清单看不出同长度改写，内容哈希看得出。
- **三档状态，而不是一档 FAIL**（这是本轮最重要的一次改设计）：哈希不一致时**当场 forcing
  补传那一个文件**（`rclone copy -I <仓库> <目标> --include config`，AGENTS §2 记录的配方）
  **再重新读一次**：
  - 读回一致 → `HEALED`（报告留行 + stdout 一行 warn + 汇总 `HEALED=`）。不这么做的后果很具体：
    这类不一致**推送永远不会自己带走**，纯检测器会在每一次换口令之后**每晚误报三次**，直到有人
    手工 forcing 为止（10-01 上午就是这么手工修的，见 §4.4 那行），观察期的告警通道一旦
    学会被忽略就等于没有；
  - 读回仍不一致 → `FAIL` + 非零退出 + ntfy 告警（「本地成功」不等于「云端有可信副本」）；
  - 网盘这一轮读不出（`lsl`/`cat` 失败或空）→ `UNKNOWN`，**不改退出码**。把抖动报成失败会让
    人开始无视告警，这一档既不是证成也不是证败，报告与 stdout 都要如实写「这一轮没证成」。
  **不变式：`HEALED` 只能由重新读过的内容换来，`rclone copy` 退出 0 不算证据。**
- **报告 `timeline/CLOUD-VERIFY.txt`**：每轮重写、**先比对后落笔**，所以它随**下一轮**时间轴
  推送才上云、从不自指（异机排查时云端看得到上一轮结论）。正因为这个顺序，本地清单里
  **不需要**给它开特例——第一版写了个 `! -name CLOUD-VERIFY.txt` 的特例，那是一句永远观测不到
  反证的死代码，改成断言「上一轮的报告确实上了云」（正向、可变异）。
  本地 `rescue-test.txt` 则**必须**从清单里摘掉：红线 §1.1 规定它只留本地，真机每晚都有这一份，
  不摘就是每晚假报「云端少一份」；同时云端若有它（10-01 真机就有过一份历史副本）→
  `privacy` 检查判 FAIL，这是 `--exclude` 挡不住既有副本、只有自证看得见的那一类。
- **红线 §1.1 落在这份报告上的形状：差异样本只到目录**（`dir_sample`，FAIL 行写
  「缺失所在目录 / 尺寸不符所在目录」而不是完整相对路径）。理由不是今天真的漏了什么——
  被校验的两棵树（时间轴产物、引擎 chunk）名字全是系统生成的——而是**这份报告本身是明文产物，
  而且随时间轴上云**，「用满 30 列写清是哪个对象」这条便利性一旦成立，将来把校验面扩到
  `system-meta/`（mounts/crontab 转储，里面全是用户路径）那天就顺着同一个 `printf` 漏出去。
  夹具因此造了一个像用户文件的对象名（`秘密-王峭楠-简历.doc`）让桩把它从云端清单里抹掉，
  断言报告**指名所在目录**且**一个字节的文件名都不带**。这条断言今天咬不住任何真实泄漏，
  它防的是那一步改动——**红线守卫要按「将来谁会踩」写，不是按「现在有没有漏」写**。
- **踩到的五个坑**：
  1. `run_cloud_verify` 第一版对**三类仓库根本没跑**（报告 `checks=2`）：borg 分支忘了往
     `repo_pairs` 里登记。E2E 全绿差点让这条混过去——所以第 1 段断言把七个检查名逐个点名，
     汇总 `checks=` 也在意。与 §4.1「CI 绿 ≠ 跑过」同一类。
  2. 夹具没有 `profile.json`：它由 `init.sh` 写，`backup.sh`/`semantic.sh` 都不产它。桩造
     假清单的靶子于是改成「现成产物 `COVERAGE.txt`（尺寸 +1）+ 自己往最新快照里放的一份
     `秘密-王峭楠-简历.doc`（整行抹掉）」，并断言两个靶子不撞同一行。
  3. **别拿 `chmod 444` 造「云端那个文件写不进去」**：rclone 默认非原地写（目标目录建临时文件
     再 rename），只读的小文件本身挡不住替换，实测那条 forcing 照样把它修好了，于是「补传失败
     → FAIL」这条断言踩在假场景上。改成让桩在 `cat` 上撒谎（第 7 段），HEALED 就只能由真读回
     一致挣到。
  4. **断言顺序=诊断真伪**：首轮变异里 m2/m10/m11 三个各坏在不同地方，却都报同一句「仍宣布
     FULLY COMPLETE」——因为退出码那条写在状态那条之前。把「哪条检查抓到了它」挪到前面后，
     三个变异各自报对自己的原因。这条已写进 AGENTS §3。
  5. **`test_portable_stat.sh` 的静态扫描又一次拦下两条**（本机 bash 5.3.20 全绿、CI 的
     macos runner 上会炸的那一类）：`rc=$rc（` 与 `检查「$name」`——变量紧贴非 ASCII 时 bash
     可能把全角括号的首字节吃进变量名，`set -u` 下 unbound 直接静默退出。同一坑第三次露头，
     所以新脚本从来不靠自觉，靠那条扫全仓 `*.sh` 的守卫。
- **守卫**：`test_cloud_verify.sh`（新，八段：全绿轮点名 / 云端多出历史仍判绿 / 同长度改写被
  抓住并当场修好且**独立复核云端内容** / 云端 `rescue-test.txt` 残留判隐私失败 / 本地演练产物
  不污染对平也不弄瞎隐私检查且报告随下轮上云 / 读不出记 UNKNOWN 不改退出码（root 下自动 SKIP
  并如实标未测）/ rclone 桩伪造 `lsl` 的两种不一致分开计数**且差异样本只到目录** / 桩伪造 `cat`
  时补传后仍不符判 FAIL）。已挂 CI（linux + macos 各一步，E2E 由十条增至十一条）。
  **15 个变异逐个咬住且各自报对原因**：哈希不比对 / 隐私检查摘掉 / UNKNOWN 记成 PASS /
  报告不落时间轴根 / 对平成双向相等 / 仓库未登记 / 缺对象不计数 / FAIL 不改退出码 /
  本地清单不摘演练产物 / `--exclude` 失效 / **HEALED 改认 copy 退出码** / 整段 forcing 摘掉 /
  forcing 少 `-I` / 自修不留 warn 痕 / **样本从「只到目录」改成写全路径**。
- **本轮未做**（别当成已做）：L2 定期全量内容核（额度可控但没必要每晚跑）、L3 异机盲恢复、
  Windows 侧 `SEM_CLOUD_VERIFY`（`backup.ps1` 没有自证这一层，与 §6 的 Windows 欠账同批）。

### 4.13 缺陷 8：仓库字节腐化在现有全部守卫下恒为绿（10-01 夜，roadmap A2a 落地）

§4.9 那次现状复核排出的第 8 条（当时记在 §4.12 的「L2 还没做」里，实际比那更宽）：
**备份系统对「存着的字节坏了」这件事是盲的**。10-01 夜的实测形状：

- 把 `borg-files/data/0/0`（一个数据段）中间一个字节翻掉 → `borg create` **退出 0**、
  `borg check --verify-data` **rc=1** 并报 `Data integrity error: Segment entry checksum
  mismatch [segment 0, offset 8]`；
- 恢复演练只抽样取回几个文件，撞不到那个块；A6 的清单自证比的是尺寸与对象数，块内腐化
  不改尺寸。**也就是说：现有 11 套 E2E + CI 的每一条断言，对这件事全绿。**

**做法**（`backup.sh` 编排层新增 `run_integrity_check`，roadmap 11 章 §2 的 A2a）：每
`INTEGRITY_DAYS`（默认 30）天，对每个已登记的 borg 仓库跑一次 `borg check --verify-data`
（整仓逐块解密+解压+校验；真机 7.6 GB 是分钟级），结论写 `timeline/INTEGRITY.txt`。
引擎调用**不进语义层、不进 `bg preflight`**（红线 §1.3 那条分工）。

**三档判定，理由是实测而不是推测**：`rc=0` PASS；`rc=1` FAIL（真发现坏数据）；
`rc>=2` 是 borg 把「仓库可能已毁」「用法错误」「拿不到锁」**塞在同一档**——实测并发持锁
（`borg with-lock` + `BORG_LOCK_WAIT=0`）给的就是 rc=2。所以只有错误原文命中锁的记
**UNKNOWN 且不改退出码**（有人同时跑 `drill.sh --force` 不该让 nightly 报「仓库已毁」），
其余按最坏情况 FAIL。这条分档与 A6 的 `HEALED/UNKNOWN` 是同一个哲学的两次应用：**flake
不配改变结论，坐实的问题必须改变结论**。

**踩到的六个坑**：

1. **ERE 分流 pattern 必须逐字抄引擎原文**。第一版写 `failed to (create|acquire) the lock`，
   看着等价，真消息却是 `Failed to create/acquire the lock` —— `create` 后面紧跟的是
   `/acquire` 不是空格，**一条都不命中**，锁 flake 被误判成 FAIL。夹具第 4 段当场把它抓住。
2. **变异又咬错了断言**（与 §4.12 第 5 条同一类，第二次露头）：m03 本想测「闸门摘掉 →
   退出码仍为 0」，实际第一版只替换了 `error` 那一行、`exit 1` 还留着，报错原因成了
   「stdout 没有那行」；改成**整段摘掉**后又发现咬住的是第 5 段（非锁 fatal）那条退出码断言——
   夹具按 1→6 顺序走，第 6 段的「不再宣布 FULLY COMPLETE」根本轮不到。最终形态是
   **只摘 `exit 1`、报告与告警都留着**，期望串换成第 5 段那句。顺带得到一个结论：
   `grep -qE 'FULLY COMPLETE' && fail` 那条是退出码断言的**冗余保险**而非专属守卫
   （AGENTS §3：冗余断言看着就像「没咬住」，这里它的证据就是没有任何单一变异能单独抓住它）。
   **另外驱动本身要加 `bash -n`**：变异把脚本改炸时 bash 自己退 2，「退出码非零」那条断言会
   替变异背锅，看着像咬住其实测的是语法（本轮第一版就因此把 m03 判成过 BAD）。
3. **期望原因串写错也会把 OK 报成 BAD**（`borg-files` vs `borg:files`）：变异实验的结论
   要看「原因对不对得上」，所以驱动里的期望串本身也是被测面。
4. `test_portable_stat.sh` 的静态扫描第三次抓到**我自己新写的代码**里变量紧贴非 ASCII
   （`$REPORT）`）。这条守卫的价值正在这里：本机 bash 5.3 不炸，CI 的 homebrew bash 与
   某些 locale 组合会炸。
5. **夹具的锁桩必须「在被校验的那一刻」才持锁**。外部提前 `borg with-lock … &` 会把本轮的
   `borg create` 一起锁住（备份本体也跑 borg），第 4 段就会测成「整轮失败」而不是
   「校验读不出」。改成 BORG 桩：只在 `check` 分支里先起 `with-lock sleep 8`、再
   `BORG_LOCK_WAIT=0` 转发真 borg、收尾 kill——其余子命令原样转发（引擎本体照旧真跑）。
6. **文档写串了一条，而且「grep 到」也只是半程**：§4.12 记「`test_cloud_verify.sh` 已挂 CI
   （linux + macos 各一步）」，而 `ci.yml` 里 macos 那一步**从来没加过**（grep 全文件只有
   linux 那一条）。本轮补上 macos 两步（cloud_verify + integrity）——然后 0b3518a 那一轮的
   实测数据说明补上仍然等于没跑：macos job 在 100 分钟上限处被砍（派工 13:22:27Z，砍点
   1:40:19，正好停在「init 向导」），排在它后面的 log_rotation / integrity / cloud_verify
   **一秒都没执行**。各步真实耗时：backup 11m、restore 13m、cloud_failure 30m、drill 28m、
   rescue 11m。两个动作：预算 100 → 180（= 已跑的 100 分钟 + 剩三步余量），并把 E2E 清单
   **按「便宜的／本轮新加的在前，30 分钟级慢桩在后」重排**——在免费 macOS runner 上，
   被超时砍掉的永远是尾部，所以步骤顺序就是覆盖优先级本身。
   教训两条：**「已挂 CI」要 grep 工作流文件核对，别拿记忆写**；grep 到了还要回头看
   `gh run view --json jobs` 里那一步的 `conclusion` 是不是 `success`（`skipped` 就是没跑）。

**守卫**：`test_integrity.sh`（新，六段：首轮点名三类仓库 + 报告不落绝对路径/文件名 +
健康轮不推告警 / 窗口节流 / `INTEGRITY_VERIFY=0` 可关 / 锁 flake 记 UNKNOWN 且不改退出码
且另一仓库仍 PASS / 非锁 fatal 三类各记 FAIL / 真损坏只有那一类判红 + 退出非零 + 不再宣布

等于没测旁路。已挂 CI（linux + macos 各一步，E2E 由十一套增至十二套）。
**9 个变异逐个咬住且各自报对原因**：窗口恒过期 / rc=1 记 PASS / 闸门只报不拦（只摘 `exit 1`）
/ 告警旁路摘掉 /
仓库未登记 / 报告不落时间轴根 / 绝对路径抄进明文报告 / 锁分流摘掉 / UNKNOWN 算进失败计数。

### 4.14 缺陷 9：演练取回后只比大小，「同长度不同内容」恒为绿（10-02 上午，roadmap A2b 落地）

**症状**：`run_drill` 把样本解出来之后，判据只有一句 `file_size "$got" == 清单里的 size`。
也就是说演练回答的是「备份里有没有一个同名字节数的东西」，不是「备份的内容是不是我原来的
内容」。§4.9 那次跨类别错配（config/system 的样本从 files 仓库里取）能被判成 PASS 之外的问题
放过去，根子也在这一句——取回了**错仓库里同名的文件**，尺寸一样就绿。

它不是孤立缺陷，是 §4.12 那一课（123Pan 上 rclone 的比较退化成只比大小，原地同长度重写永远
推不上云而 `copy` 照样退出 0）在**取回这一侧**的镜像：同一个「尺寸等于内容」的错误假设，
一条躺在推送上，一条躺在演练里。A6 把推送那侧封住了，这侧还开着。

**做法**（`bg manifest --hash-drill-samples` + `semantic.sh:file_sha256`）：备份期密封清单时，
给**当晚抽中的那几条样本**记源文件的 sha256；演练期解包后比内容。报告据此有两种依据，逐条写明：
`PASS [files] …/note.txt (8 B, 内容哈希一致)` / `PASS … (3 B, 仅比大小：清单未记内容哈希)`，
汇总行 `RESULT: 6 PASS / 0 FAIL（抽样 6；内容哈希 5，仅比大小 1）`——**两条计数之和等于 PASS
数**本身就是断言（有条目的依据没写进报告就对不上账）。FAIL 行必须说清坏在哪一层且为什么旧口径
看不见：`（内容哈希不符：清单 … ≠ 取回 …；大小倒是一致（8 B）——只比大小看不见这一类）`。

**三个决策，都跟 roadmap 原文有出入，写清楚**：

1. **只记样本，不给全量 ≤N MB 文件算哈希**。roadmap 11 章 §2 的原话是「给 ledger 里 ≤N MB 的
   文件记 sha256」，落到实现就是**每晚多读一遍整盘**，换来的证据只在当天抽中的 5 个文件上用过。
   成本与收益差两个数量级，所以收窄成「备份期就算好当晚那 5 个」。代价：跨天跑 `drill.sh
   --force` 或夜间抽样换了一批文件时，清单里没有对应哈希 → 自动退回比大小，**且如实标注**。
   这是设计上允许的降级，不是漏洞。
2. **哈希记在备份期的源文件上**，不记在归档、也不记在演练期。演练期（可能已是 30 天后）源文件
   被正常改过，比出来的就是假失败；「取回时再算」则根本不算内容比对。归档侧本来也没这条路：
   borg 1.4 的 `list --format '{sha256}'` 取不到逐文件哈希（research/11 §2 实测）。
   配套 TOCTOU 闸门：记之前要求「源文件存在 + 是普通文件 + `st_size` 与归档条目一致」，
   任何一条不满足就**不记**——宁缺毋滥，绝不拿 size 冒充内容一致。
3. **记哈希的抽样与 drill 的抽样共用同一个 `select_drill_samples`**（同 count、同默认「今天」
   种子）。两处各算各的＝「记了没人用／用的没记」，而这种不一致在 E2E 里是全绿的。
   唯一现场信号是 stderr 那行 `[manifest] 演练样本内容哈希：n/picked 个已记入密封清单`，
   `0/N` 就意味着这层证据整段退化了；分母用**实际抽中条数**而不是 `--sample-count`（count 是
   上限，写 `0/99` 等于没有信息）。

**隐私与兼容**：`sha256` 只进 `manifest.json.enc`（和演练期临时解封那份），run.json 与
MANIFEST/STORY/COVERAGE 一个字节都不写（单元测试直接扫明文产物里有没有 64 位十六进制串）。
`MANIFEST_FORMAT` 保持 `backguard/manifest/1`——`rescue.sh:428` 逐字比它，改版本号等于让旧
逃生脚本读不了新清单；而它的 awk 状态机忽略未知键，多一个字段是向后兼容的。
顺带被真实崩溃教育了一次：`Entry(**e)` 把清单条目结构钉死成四个字段，加了 `sha256` 之后
`compute_run` 当场 `unexpected keyword argument`——现在统一走 `entry_from_dict`（渲染只认白名单
字段，清单侧允许带额外字段）。

**踩到的五处**：

1. **夹具的 `borg create` 用相对 include ⇒ 记哈希静默记 0 条而全链路全绿**。归档里是
   `src/Documents/…`，而 `hash_drill_samples` 按 `/ + 归档路径` 找源文件，永远找不到。
   改成绝对路径 include（与生产同形），并把这条做成变异 `m08`。
2. **`BG` 必须指 `semantic/bg.pyz`**：`semantic_bg()` 优先用 zipapp，直把 `BG` 指向
   `bg_semantic.py` 在夹具里是 Permission denied（CI 每轮会 diff/重建 pyz，改了 .py 不重跑
   zipapp 就是「变异没落上」——变异驱动里那条 pyz 重建就是为这个加的）。
3. **单元测试里三种「不记」互相顶掉**：`test_hash_skips_oversize_missing_and_rewritten` 第一版
   把「create 之后被改过」那条写成 size=999，而 999 先被**超大**规则拦下——把尺寸闸门整段摘掉
   （变异 `p03`）测试照样全绿。改成超大条目按真实尺寸写、被改过的条目 size=4 而磁盘上 7 B，

   单元测试里的样子。
4. **夹具调的是生产 `seal_manifest` 而不是自己拼一遍参数**（`SEM_DRILL_COUNT=99`、
   `SEM_DRILL_HASH_MAX_BYTES=2048` 走环境变量注进生产函数）。否则「生产 seal 与 drill 口径不
   一致」这一类整段测不到——§4.9 的跨类别错配正是同一个遮罩。
5. **变异「没咬住」有两种原因，别都当成实现的问题**：m04 第一轮报的是「没有 E2E-FAIL 行」，
   查下去不是断言太弱，而是**断言自己先死了**——`basis="$(grep -o '内容哈希 [0-9]*，仅比大小
   [0-9]*' "$RT" | head -1)"` 在无命中时 grep rc=1，`set -euo pipefail` 让夹具在那一行直接退出，
   后面的 `[[ -n "$basis" ]] || fail` 永远轮不到（AGENTS §2 那条「可容忍失败用 `; true` 中和」
   的第 N 次露头，这次露在**新写的守卫**里）。改成 `{ grep … || true; } | head -1` 之后 m04
   当场咬住。**推论：`X="$(grep …)"` 形式的断言，「取值为空」本身就是被测情形时必须显式中和
   退出码**，否则它是一条死断言，而它死法与「变异没落上」一模一样。

**守卫**：`test_bg_semantic.py::TestDrillContentHash`（记的集合＝抽的集合 / 超大·缺失·被改过

### 4.15 缺陷 10：夹具按日期腐化——同一条断言昨天绿、今天红（10-02 上午，A2b 门禁时撞上的）

跑第二遍全套 E2E 时 `test_restore_e2e.sh` 断言 7 报了
「STORY 没写时间轴口径的上一次备份」，而 STORY 里明明写着 `上一次备份是 2026-10-02 10:03`。
数字没错、口径也没错，**错的是那个 10:03 是「跑测试的那一刻」**：

- 断言 7 要验的是「上一次备份」取自**时间轴目录名**而不是引擎归档，于是种了一份
  `timeline/2026-10-02/0234-night`，然后以 `SEM_TIME=2026-10-03T02:34` 生成快照，期望读到
  `2026-10-02 02:34`；
- 可它前面的两发 `generate_semantic`（断言 6 前置、6c）**没传 SEM_TIME**，语义层就用真实现在，
  快照落在 `<今天>/<现在HHMM>-<时段>`；`semantic.sh` 挑「上一份快照」用的是
  `find | LC_ALL=C sort | tail -1`——**只要今天的日期恰好等于种子日期（10-02），而时刻晚于
  02:34，那两发真实时间的快照就排到种子后面**，被选中的「上一次备份」成了跑测试的那一刻。

也就是说这条断言的绿不绿取决于**在几号几点跑**。10-01 写它的时候一切正常（种子 10-02 排在
「今天 10-01」之后），10-02 当天准时腐化；CI 也一样会红——runner 的本地日期撞上种子那天、
时刻过 02:34，就红在恢复链路的守卫上，而那跟被测代码毫无关系。

**修法**：夹具里每一次 `generate_semantic` 都显式给 `SEM_TIME`（09-30 / 10-01），让「种子快照
是最新的一份」这件事不再依赖墙上时钟。**通则**：只要产物目录名/文件名里带日期，而断言又按
排序取「最后一个」，那夹具里**所有**写入该树的调用都必须写死时间——与 §4.11 日志轮转那条
「种子 mtime 必须 `touch -t` 写死，同秒并列会让留哪几份变成运气」是同一条规矩的两个方向：
**按时间/名字排序做判定，就不许有任何一个输入来自现在**。查法很便宜：`grep -n 'date +\|date -d'
test_*.sh` 看还有谁在断言里拿现在比（本轮查过，其余十一套没有）。



### 4.16 缺陷 11：CI 守卫对「它唯一能验的环境」是瞎的（10-02 下午，Windows 保留策略首轮判红）

`cbed5d1` 把 bash 侧的 `prune_local_timeline` 移植成 `Prune-LocalTimeline` 并挂上 windows job
（`Assert local timeline retention`）。首轮 CI 红，而报错本身没法定位：

```
残留 0900-seed, 0900-seed, 0900-seed        ← 三份种子都没被裁
… FULLY COMPLETE                            ← 同一轮里产品宣布自己跑完了
```

**「没删」在这条 lane 上有四种长得一模一样的坏法**，而当时的守卫把它们压成同一句话：

1. 函数根本没被调用——`semantic.ps1` 在 `generate` 之前有五处 early `return`（bg 不可用、
   无可导出清单、convert 失败、generate 失败、异常），任何一处都让保留策略整段不执行；
2. `SEM_TIMELINE_KEEP` 没读进子进程 → 回落默认 14 → `$snaps.Count -le $keep` 直接返回；
3. 深度判定认出 0 个候选（第 4 层在 Windows 上是反斜杠路径，切分口径与 bash 不同形）；
4. 函数内抛异常，被 `backup.ps1` 的 `catch` 接走并继续走 `FULLY COMPLETE`——§1.3 的
   非致命分层在这里恰好是**遮蔽器**：旁路炸了不影响本体，所以本体那行绿字什么都不能排除。

**修法（三件事，按诊断价值排序）**：

1. **产品自己吐证据行**：`[semantic] timeline-retention window: keep=N snaps=M`，一行三个事实
   （被调用过 / keep 读到了 / 第 4 层认出几个）。**必须纯 ASCII**——这条匹配发生在**父进程**
   读**子进程** stdout 的地方，中文要先过 `[Console]::OutputEncoding` 解码，糊成乱码时守卫会
   红得毫无道理（报错还指着「保留策略坏了」，而真实原因是编码）。
2. **守卫拆两段，且断言顺序 = 诊断**：第一段 `. semantic.ps1` 后直接调函数（证「函数本身对」），
   第二段把 `backup.ps1` 当**子进程**跑（脚本内 `exit` 会终结整个宿主会话，所以必须子进程），
   先断 `FULLY COMPLETE` → 再断证据行存在（缺 → 「根本没被调用」）→ 再解析 `keep=`/`snaps=`
   （≠1 / ≠6 → 分别对应坏法 2 与 3）→ 才轮到「种子没被裁」「不合规那份被删了」「日期壳还在」
   「退出码不是 0」。每一步 `::error::` 写的都是**哪一种坏法**，不是「失败了」。
   第一段还必须先清空 `$stage`：上游步骤留下了真快照，`KEEP=1` 的窗口形状就不确定。
3. **本机补上一条 pwsh 运行时**（这一条才是「深度」所在）：
   `docker run --rm -v "$PWD":/repo:ro mcr.microsoft.com/powershell:lts pwsh -NoProfile -File
   /repo/test_prune_logic.ps1`——25 分钟一轮的盲跑变成几秒。它覆盖语法、cmdlet 参数绑定、
   排序键、叶子白名单、空壳级联、`KEEP` 的默认/关闭/垃圾值分支；**不**覆盖反斜杠路径与大小写
   不敏感（Linux 造不出来）、也不覆盖 Task Scheduler 注册的 `powershell.exe` 5.1 那台宿主。
   所以 windows job 那发守卫照旧要跑，两发的分工是「逻辑先在这里收敛，接线与环境留给 CI」。
   `test_prune_logic.ps1` 自己也要按规矩收流：`Write-Host` 走 information(6)、`Write-Warning`
   走 warning(3)，只收 `6>&1` 的那条告警断言是**恒假**的死断言。

**容器第一轮就咬出一个真移植缺陷**：空日期壳的级联**只走了一层**。bash 侧
`find … -empty -delete` 隐含 `-depth`（深度优先，子先于父），而 PowerShell 写成「筛出空目录
→ 删」时没有这个顺序，`DD` 壳收掉了，`MM` 与 `YYYY` 壳永远留着。修法是
`Sort-Object { $_.FullName.Length } -Descending`（子路径必长于父路径）并把判空放在排序**之后**
——惰性管道于是先删子、再判父。

**为什么两套夹具都没测到**：bash 那份 `test_timeline_retention.sh` 的 12 份种子全挤在同一个月
（`2026/09`），**月份壳永远不会空**，级联第二层压根没机会露头；PowerShell 侧此前没有可跑的
运行时，窗口里只断言了「快照裁没裁」。补种 `2025/03/04` 与 `2026/01/02` 两份（跨年 + 跨月）之后
§2b 断「年壳必须没」，变异把 `-empty -delete` 换成 `-empty -print0 | xargs -0 rmdir`（= 不深度
优先）当场报 `旧快照的年壳没收掉——级联只走了一层`。容器 harness 的场景 1 与 windows job 守卫
第一段（`$farMon`/`$farYear` 也得没）是同一条契约的另外两份锁。

**通则**（三条，都进 AGENTS）：

- 「本机没有 X」不是「只能拿 CI 当解析器」的理由——先花一次拉镜像的成本把 .ps1 变成可本地变异
  的被测面，否则每轮 25 分钟里你只是在猜。
- 报错要写成**哪一种坏法**：一个观察点被多种成因共享时，断言的**先后顺序就是诊断本身**
  （与 §4.12「一条主张配一个专属变异」同一条规矩的另一面）。
- 先断言实现**看见了输入**（`snaps=` 计数），再断言它把事做对了：前者把「判定错」和「没跑」分开，
  后者只在「跑了」的前提下才有意义。


### 4.17 缺陷 12：引擎 JSON 的时间被宿主转成 DateTime，第二次备份起语义层静默不产出（10-02 下午，§4.16 那道守卫第二轮就抓到）

上一节那行 ASCII 证据按其设计报了它该报的东西：

```
WARNING: [semantic] generate 失败（见 backup.log），跳过     ← 子进程唯一的 [semantic] 行
=== 第一段（函数本身）OK：裁两份、留一份、不合规那份活着、空壳收掉 ===
```

也就是说**保留策略本身没问题**，坏的是它前面那一步——四种坏法里的第一种。排除过程全靠能跑的
实验，没有一条靠读码猜：

1. `convert` 是成功的，而同一份 restic 清单里的 node `mtime` 也是 Go 的 RFC3339Nano（小数位
   1/4/7/9 都可能），能过就说明**那台 runner 的 python ≥3.11**——实测 `/usr/bin/python3`（3.9.6）
   对 9 位小数直接 `ValueError: Invalid isoformat string`，3.14 通过。于是「小数位位数」不是本轮
   那条腿（但它是同一条兼容约束的另一面，见下面第 4 条）。
2. 本轮唯一新增的入参是 `--parent-time`，值来自 `$prev.time`（首备没有上一份，所以从没走到过）。
3. 容器里的 pwsh 7.2 对 `ConvertFrom-Json` 的该字段交回 **String**（`2026-10-02T06:31:11.447503458
   +00:00` 原样）——说明这个类型是**宿主版本相关**的，不是稳定的。
4. 把新加的 `Format-IsoTime` 退化成 `[string]$Value` 做变异，`[datetime]` 那条断言当场打出
   `10/02/2026 06:31:11`：正是 bg 的 `parse_iso` 读不动的形状。**结论**：windows runner 的 pwsh
   （7.4+，与真机 Task Scheduler 用的 `powershell.exe` 5.1 同一类）把 `time` 交回成 `[datetime]`，
   一旦拼进命令行就是**文化相关**的串；`convert` 只存不解析所以照报成功，`generate` 才崩。

**为什么这么久才露头、以及为什么它在真机上不响**：这条分支只在「存在上一份归档」的那一轮走得到，
而 CI 的 windows job 每轮新建仓库、只跑首备（与 §4.13 记的「流水线空转」同一条结构性盲区）；真机上
它是**静默降级**——§1.3 的旁路不许带走本体，于是 `backup.log` 里一句 warning、结论行照打
`FULLY COMPLETE`，人能看到的只是「时间轴不再长新快照」。

**修法（两侧各一行的那种）**：

- PowerShell 边界 `Format-IsoTime`（`semantic.ps1`）：`[datetime]` / `[datetimeoffset]` 走
  `ToUniversalTime()` + 固定 `"yyyy-MM-ddTHH:mm:ss'Z'"`，String 原样透传——不碰文化、不留类型歧义。
- Python 侧 `parse_iso`：小数秒补齐/截断到 6 位。这条**不是**本轮的腿，但它是 §2「Python 兼容」
  的同一条约束（3.9 + restic 清单）——restic 的位数不由我们决定，兼容版本就不该由它决定。

**顺手补的两处诊断面**（都属于「报错要写成哪种坏法」的延伸）：

- 「（见 backup.log）」这句话在 CI 里等于没说：`bg generate` 的 stderr 全进子进程的
  `backup.log`，非致命旁路不往 stdout 甩 traceback，而 `Push debug logs` 上传的 `diag.txt` 是
  步骤 5 的采集，不含子进程那份日志。→ windows 守卫的五个失败分支各加 `Show-ChildLog`（尾 12 行，
  只进作业日志，**不进那份匿名可下载的 release 资产**）。
- 守卫开头加一行 `probe:`，把「这台宿主把 JSON 的 time 交回成什么类型、裸插值长什么样、pwsh 几版」
  写进作业日志——下次不再需要反推。step 的 `run:` 块还能用 `Parser::ParseFile` 在 Linux 容器里
  纯语法检查（本轮 203 行 PARSE-OK），盲写的 PowerShell 不必拿 25 分钟去试括号。

**门禁**：`test_prune_logic.ps1` 场景 7 六条（String 透传 / Utc / Local 形状 / 不许出现 `/` /
`DateTimeOffset` 折算回 UTC / 「裸 ToString 就是那条坏串」——最后一条钉住变异落点，证明前五条
不是空转），摘掉 datetime 分支 → `PRUNE-LOGIC-FAIL count=4`；新增

### 4.18 缺陷 13：`bg convert --engine generic` 从来没跑通过（10-02，复现 §4.17 时顺手撞见）

排查 §4.17 时想用最小夹具单跑一次 `convert`，换成 `--engine generic` 立刻
`TypeError: parse_generic() takes 1 positional argument but 3 were given`（`cmd_convert.load()` 里那句共用的 `parser(...)`）。
成因是**调用点只有一处、分支有三条**：`cmd_convert.load()` 里
`parser(text, args.strip, known_dirs)` 同时喂 restic/borg/generic，前两个在加 strip/dirs 时
改了签名，generic 没跟。生产只走 borg（`semantic.sh:305`）与 restic，所以这条 advertise 在
`--engine` 的 choices 里的路径从未被调用过——它不是「结果不对」而是「从没执行到」，
这类缺陷光读代码看不出来，只有真调一次才露头。

修法不是只补两个参数：`parse_generic` 原先连 `_norm_path` 都没过，`C:\Users\neb\a.txt`
会原样落进清单（盘符段、反斜杠都在），所以按 restic/borg 同形补齐（arity + 归一化 +
`dirs` 出参占位）。`generic` 的输入是别处已剥过前缀的 entries 切片，strip 默认 0 时行为不变。

守卫：`test_bg_semantic.py::TestParsers::test_parse_generic_matches_other_parsers_arity`
（直接调三参版，验 strip 与反斜杠）+ `test_convert_engine_generic`（走 `bg.main` 端到端，
含 render_snapshot，防的就是「单元绿但调用点形状还是错的」）。两条变异各摘一处——
签名摘回 1 参 → 两条都炸 TypeError；`_norm_path` 摘成原样 → 两条都 fail 在路径断言上。

**通则**：多分支共用一个调用点时，「这条分支在不在清单里」和「这条分支调不调得通」是两件事；
前者看 `choices=[...]`，后者要逐分支各调一次。


### 4.19 缺陷 14：restic 分支从没跑成过一次备份，且「本地保留」不回收字节（10-02 傍晚）

§4.18 那条通则的第二发，这次炸的是引擎侧不是语义层。`backup.sh` 有一条
`PLATFORM == windows` 的 restic 分支（`backup_restic_class`，git-bash/MSYS 下用），
10-02 第一次拿真 restic 把它跑起来（`XDG_CONFIG_HOME` 指到临时配置、`PLATFORM=windows`、
`SKIP_WEBDAV=1`），现场是**三类全红**：

```
Fatal: Please specify repository location (-r or --repository-file)
[ERR] [config] restic backup 失败 (exit 1)
...
[ERR] === Backup FINISHED WITH ERRORS (3 个档案失败) ===
```

原因是 `init` 写了 `-r "$repo_path"` 而 `backup` 没写——restic 不记得上一条子命令用的
哪个仓库。这一分支之所以从没露头：真机 Windows 走的是 `backup.ps1`，CI 的 windows job
也只跑 ps1，**没有任何一条路径在 Windows 上跑 `backup.sh`**；而 `PLATFORM` 又是由
`uname -s` 推出来的，所以 linux/macOS 夹具也进不去这个分支。它和 §4.18 那一发是同一个形状：
「`--engine`/`PLATFORM` 的 choices 里有这条路」≠「这条路调得通」。

第二发在同一条命令上：`restic forget` **不带 `--prune`**。引擎帮助页原话「forget … really
only deletes the snapshot object in the repository … In order to remove the unreferenced
data … see the "prune" command」；实测（9 份日快照，每份 6 MiB 独有数据、之后从磁盘删掉）：

| 动作 | 快照数 | data/ 包数 | 仓库大小 |
|---|---|---|---|
| 预置完 | 9 | 18 | 55448 KiB |
| `forget`（生产现状） | 8 | **18** | **55444 KiB**（只有索引重写） |
| `forget --prune` / 再 `prune` | 8 | 16 | 49264 KiB |

也就是说「本地保留 7d/4w/6m」在 `backup.sh` 与 `backup.ps1` 里都只把快照**藏起来**，
字节永远留着——而 `backup.ps1:174` 那句「本地已 prune，云端保留全部历史」的前提整个不成立。

修法（两份实现对齐同一张 rc 表）：`backup` 补 `-r`；`forget --keep-* --prune`；
`rc == 3`（restic 的「有源文件没读到，快照已落库但不完整」，与 borg `create` rc=1 同档）
只 warn 不判败，其余非零判本类失败。ps1 侧原先对 `forget` 的退出码**一条都没看**，现在
补上同一发（`rc=3` → `Write-Warning`，非零非 3 → `throw`，被既有的逐类 catch 计进
`engine=` 并不宣布 COMPLETE）。

守卫 `test_restic_retention.sh`（真 restic，linux job 一步；六段）：
①三类全部成功且退出 0；②策略真裁了快照 **且**字节真回收（`running prune` 一行 +
释放 ≥1 MiB + 包数下降）；③回收后 `restic check` 过（prune 删错东西比不删更糟）；
④`rc=3` 只告警、仍宣布 COMPLETE；⑤`rc=12`（桩只对 `forget` 换错口令、其余转发真二进制）
必须让本类失败且不宣布 COMPLETE；⑥`backup.ps1` 的同形（静态：带 `--prune` + 有 rc=3
分支 + 检查退出码——ps1 的行为面本机跑不了，而 CI 的 windows job 每轮新建空仓库，
`forget` 在那儿一份都裁不掉，「没带 --prune」与「带了」长得一模一样，所以只能钉形状）。
变异六发各自咬住：m1 摘 `-r` → 第 1 段；m2 摘 `--prune` → 第 2 段；m3 摘整段 rc 判定 →
第 5 段；m4 摘 rc=3 容忍 → 第 4 段；m5/m6 摘 ps1 的 `--prune`/rc 判定 → 第 6 段。
**夹具的一处死法（第一版就把「没 prune」测成了「prune 没活干」）**：预置快照若只往同一
目录累加文件，当晚的新快照仍引用全部旧内容，prune 无字节可回收——每份独有数据必须在
下一份之前从磁盘删掉。

**通则**：跨平台/跨引擎的分支，「文档里支持」和「有一条路径真跑过」是两件事；而**低频
分支的测试要连它的副作用一起测**（这里＝仓库尺寸），只数快照条数的断言在「forget 没带
--prune」下照样绿。

### 4.21 欠账 16：A4 的 Windows 那一半——轮转接上了，但 `finally` 在这条路上不能用（10-02 傍晚）

### 4.24 缺陷 19：Windows 夜间从未真跑完过一轮——5.1 的 `Stop` 把引擎的 stderr 变成终止性异常（10-02 夜，任务 #37）

露头的方式是 CI 自己红：run `37003329872` 的 windows job 第 16 步（`Cloud verify logic on
Windows PowerShell 5.1`）死在 `& rclone lsl $Dest 2>$null`，报 `RemoteException` /
`NativeCommandError`。这不是网盘的问题，而是**这一档宿主的一条语义**，于是把它跑成一手事实：
5.1 探针（`probe_windows_ps51.ps1` 事实 3，宿主 PS 5.1.26100.33438）原样吐回的三行是

```
tee2>&1=THREW RemoteException  redirect2null=THREW RemoteException  pipeOutNull=THREW RemoteException
```

也就是：**`$ErrorActionPreference="Stop"` 的作用域里，原生命令只要往 stderr 写一行就抛终止性异常**，
`2>&1 | Tee-Object`、`2>$null`、`2>&1 | Out-Null` 三种形态全抛；pwsh 7 一条都不抛。而
`backup.ps1` 顶部正是 `Stop`，而备份引擎的**正常输出偏偏写在 stderr**（restic 的进度、rclone 的
`NOTICE: Config file … not found`），而 Task Scheduler 注册的命令行是
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File backup.ps1`。

**推论是这一发最贵的部分：Windows 设备的 nightly 从来没有真跑完过一轮。**第一次备份断在
`restic backup`，第二次起断在 `restic init` 那条幂等分支（它靠的就是「忽略报错」）。而 CI 的
产品轮用 `pwsh.exe`，7 不抛——**整个观察期里 windows job 全绿**，绿的正是那一步唯一测不到的东西。
坏的一半还在旁路：语义层的调用点是 `catch { Write-Warning "[semantic] 生成失败（不影响备份）:
$($_.Exception.Message)" }`，于是这条路上「明文层整段从未产出」与「语义层抖了一下」长得一样，
而结论行照打 `FULLY COMPLETE`（§1.3 的非致命分层在 5.1 上退化得悄无声息）。

**修法按作用域，不按文件**：每个含原生命令的函数**首句**把 EAP 压回 `Continue`——偏好变量按
**动态作用域**解析，赋值是函数作用域的，出函数自动回到调用方的 `Stop`，所以 cmdlet 那一份纪律
一点没丢；嵌套函数（`semantic.ps1` 里的 `Invoke-Bg`）也要自己声明，「外层忘了」就是这一发之前
漏掉九处的成因。落地：`backup.ps1` 十处函数入口 + 新抽出的 `Push-TreeToCloud`（云端推送循环原来
裸在主流程里，两个 rclone 调用坐在 `Stop` 作用域正上方；抽成函数而不是就地塞 scriptblock，是为了
让「作用域自己声明一档」这条规则保持**机械可查**），`semantic/semantic.ps1` 两处。**判定一律不靠
异常**：`throw` 在 `Continue` 下同样是终止性的，所以 try/catch 的结构与 `$LASTEXITCODE` 的口径
一处没动。

**守卫两头**：①`probe_windows_ps51.ps1` 事实 5 用 **AST** 扫每个原生命令调用点，要求它所在的
`ScriptBlockAst` 在调用之前有这条赋值（容器实测 `nativeCalls=17 violations=0`，并带
`nativeCalls>=10` 的存活下限——只扫到 3 处就等于规则自己失效）。用解析器而不是正则，是因为
「数不准」在这里不是精度问题，而是**漏掉的那一处就是炸点**。②ci.yml 新增
`Backup round on Windows PowerShell 5.1`：拿 5.1 真跑一整轮产品脚本（子进程 `powershell.exe -File`，
跑在 pwsh 那轮已建好的仓库上，所以连「已初始化」的幂等分支一起走）。它的判定是
rc/`FULLY COMPLETE` → **本轮真的产出了新的 `MANIFEST.txt`** → 语义层自己那行 `[ OK ] [semantic]`
收尾必须在场（`semantic.ps1` 的每一条降级路径都在它之前 return）→ 输出里不许出现
`RemoteException`/`NativeCommandError`，后三条专测「被 catch 悄悄吞掉」那一半，只断言退出码抓不到它。
**四条判据全用 ASCII 写**：这一步的正文被 Actions 写成不带 BOM 的临时 `.ps1`，中文在这档宿主上
要么炸解析器、要么安静变乱码——后者更坏，`-match '……失败'` 会恒不命中却照样打绿（详见 §11 续 7

### 4.25 欠账 19：`backup.ps1` 的 restic 保留策略补上行为面（10-02 夜，任务 #36）

§4.19 末留的那发：ps1 侧的 `forget --prune` 至今只有**静态**守卫，因为 CI 的 windows job 每轮

`System.Object[]`），绑不进 `Chk([bool]$cond)`，于是「日志没落笔」这条本该报 FAIL 的断言报的是

### 4.26 欠账 ⑧：Windows 的权限面——一次 icacls 收紧四棵树，而「整棵树」靠的是动态继承（10-02 夜，任务 #38）

§2 那条「权限面：整树归一化，别再补 glob」在 bash 侧是 10-01 用真机实测换来的，ps1 侧到今天下午
**一次都没做过**。Windows 上的形状不一样：没有 chmod，而**任何新建目录都从父目录继承 DACL**，
`%APPDATA%`、`%LOCALAPPDATA%`、`%USERPROFILE%` 的默认继承里都带着 `BUILTIN\Users`——也就是同一台
机器上的别的账号能遍历并读到 `secrets.env`（restic 口令）与 `age\` 私钥目录。T1.6 要把 dogfood 扩到
Windows 那一台（§6），所以这一发必须赶在装机之前，而不是等真机第一夜之后再补。

**做法与 bash 侧同一取舍**：不点名文件、也不逐文件跑 icacls（几千个 chunk 扫不起），只对四棵**根**
各做一次 `icacls <根> /inheritance:r /grant:r "*<当前用户 SID>:(OI)(CI)F"`。子项跟着变靠的是
**动态继承**——Windows 的继承 ACE 不是创建时烤死的，父档 DACL 一改，没主动断开继承的子项
（restic / rclone / PowerShell 建的那些都不曾断开）**当场**重算自己的有效 DACL，所以整棵树一次调用
就归一，`/T` 那种递归遍历是多余的。这条机制本身就是这一发成立与否的前提，所以它是一条**必须被跑一次
的断言**（场景6 的 `AreAccessRulesProtected -eq $false`），不是注释里的信念。
四棵树 = `$CONF_DIR` / `$LOG_DIR` / `$BACKUP_BASE` / **`%USERPROFILE%\PartiverseBackup`**：最后一棵是
默认仓库根的**父**目录，`Install-Deps-Windows` 把 restic/rclone 落在它的 `bin\` 下，也就是住在
`$BACKUP_BASE`（同级的 `repo`）之外——点名清单少写这一条，就又是「补了 `*.log` 却漏 `age/` 」那一形。
SID 由 `WindowsIdentity::GetCurrent()` 现取（写死一条＝在别人机器上把敞口交给错的账号）。
**非致命**（§1.3）：icacls 返回非零只告警并计入 `bad`，绝不终止这一轮——收紧失败＝维持原状，
把一次旁路失败变成整轮失败会让告警通道失去信任。调用点两处（夜间轮 `Start-PartiverseBackup` +
初始化向导），都排在 `New-Item` 建目录之后、`Test-Path "$CONF_DIR\secrets.env"` 之前。

**守卫 `test_perms_logic.ps1`**（新，容器 **23 条 ok + 1 条如实 Skip**，变异 **12/12 CAUGHT**，台账在文件头）：
桩那半负责 argv 逐字、非致命三档、返回流干净（`applied`/`bad` 的计数一旦被引擎噪音混进成功流就失真，
与 `Push-TreeToCloud` 同一课）、两处调用点的存在与**顺序**；真 icacls 那半（场景6）负责
「继承真的断开、子项真的靠动态继承跟着变、自己仍然写得进去」。**桩只会报告它被叫什么，不会报告
DACL 变成了什么**——所以场景6 是这一发唯一的行为证据，而容器里压根没有 icacls，它整段 Skip 并如实计数。

**这一发最值钱的一条教训：夹具要自己造出「要防的那个起点」，别赌宿主的默认 DACL。**
场景6 第一版直接读 `%TEMP%` 下新建目录的继承 ACE 当起点，两种坏法都在里面：① 免费 runner 镜像的默认
DACL 本来可能就干净 → 起点为空 → 「只剩自己」这条断言恒真，摘掉 `/inheritance:r` 照样绿（死断言）；
② 更要紧的是 `Get-Acl` 交回的 `IdentityReference` 在 Windows 上通常**已经翻成账号名**
（`MACHINE\user`、`NT AUTHORITY\SYSTEM`），而 `WindowsIdentity` 给的是 **SID**，拿名字比 SID 会把
「自己」也算成外人——一条**只有 windows runner 才露头**的假失败，容器里永远看不见。现在夹具先给外层目录
显式授给 `BUILTIN\Users`（`S-1-5-32-545`）让内层继承到它，比较口径全部归一到 SID（`Translate` 到
`SecurityIdentifier`，已经是 SID 时**别**自译——同类型 `Translate` 抛 `InvalidCastException`），
种子 icacls 失败时走 `Skip` 并写明「没有证据不等于通过」。

**另一发在容器里就露头的假失败**：场景4 那条 grant 形状断言第一版写成
`($fnBody -match '\*\$' + 'Sid\}:\(OI\)\(CI\)F')`——字符串先拼再当模式，且产品里写的是 `${Sid}`，
于是模式找的是 `$Sid}`。改成一条完整模式 `'\*\$\{Sid\}:\(OI\)\(CI\)F'`。同一场景里
`IndexOf('secrets.env')` 当顺序锚点也会**先撞上函数自己的注释**（注释里就写着「读 secrets.env 之前」），
锚点必须是**语句**（`Test-Path "$CONF_DIR\secrets.env"`）。

**CI 挂三步**（`grep -n test_perms_logic .github/workflows/ci.yml` 可核）：`Permission surface logic`
（pwsh，产品轮之前）、`Assert permission surface wiring`（pwsh，读上面那轮**产品轮真留下**的
`$env:APPDATA\PartiverseBackup` / `logs` / `$env:RUNNER_TEMP\repos`）、`Permission surface logic on
Windows PowerShell 5.1`（末尾）。接线那一步的判据取 `AreAccessRulesProtected` 而**不是**
「有没有 `BUILTIN\Users`」——后者在这条 runner 上可能本来就干净，拿它当唯一信号就是一条恒真的死断言；
「根被断开继承」只有那一次调用能产出。windows job 命名步 **19 → 22 步**，`shell: powershell` 的正文
**6 → 7 步**（逐 step 按字符 >0x7F 扫过，violations=0）。

**不覆盖的（在这里注册，别假装覆盖）**：① 同机管理员/`SE_BACKUP_NAME` 仍可 take ownership 读进去——
这条面挡的是**同机普通账号的顺手遍历**，与 bash 侧 0700/0600 同口径；② Task Scheduler 换成别的账号
运行时的情形没测（产品假设注册用户＝建目录用户）；③ `init-keys.ps1` / `rescue.ps1` 建的目录由**下一轮**
夜间轮收紧（它们自己不调用这一发）；④ 场景6 的行为证据只有 windows runner 拿得到，容器那一步永远是 Skip，
所以这一发的「真做到了」要读 CI 那一步的 `skipped=0`，而不是读容器的 OK。

## 7. 关键设计决策与实测教训（新会话必读，防重蹈）

**设计定案（用户亲自拍板，勿擅改）**：
- 命名体系：`<设备名>-<系统>` 全小写、不含 OS 版本（大小写不敏感网盘的安全交集 + 系统升级不分裂历史）；品牌原名进 `profile.json`；点转连字符。
- 存储层：rclone 统一管理，`BACKUP_TARGETS` 多目标（用户原话「后面还会有其他 remote 加入」）。
- 密码管理器：rbw（Bitwarden CLI）经引擎原生 PASSCOMMAND 做可选 sidecar，定位是纸质恢复码的第 2 份副本，**绝不替代**；`drill --from-bitwarden` 周期真实验证。
- 云端策略（未来）：B2 主存 + R2 零出口恢复双写（Phase 1）。

**实测教训（全部有提交记录可查）**：
- **时间口径**：borg 1.4.5 的 info start 是 naive 本地时间（不是 UTC——CI 的 TZ=UTC 曾造成盲测误判）；launchd 幻影 +8h 事故后 parent-time 改由归档名解析；Python 3.9 `fromisoformat` 拒绝 `+0800`，parse_iso 容错 ±HHMM/Z；demo/测试时间一律 naive。
- **launchd 受限 PATH**：`command -v age` 扑空 → `find_age` 补 /opt/homebrew、/usr/local；系统 python3 3.9 兼容必须保持。
- **bash 3.2/5 双轨** + `set -euo pipefail` 陷阱 + shellcheck 三连（SC2154/SC2318/SC2199）——细则见 AGENTS.md §2。
- **age 只读 /dev/tty**：`printf | age -p` 喂不进，expect 驱动（init-keys.exp）为正解。
- **123Pan WebDAV**：大小写不敏感、DirMove 500、大文件偶发 500——目录迁移用 copy+验证+purge；新 remote 先跑 `test_remote_caps.sh`。
- **隐私级 bug 案例**：单文件曾被两级细化误写成目录名 → 引入 known_dirs 目录证据机制；2026-09-30 又抓到残留回退（known_dirs 缺失时仍允许两级名，纯文件清单下 `Pictures/IMG_0001.jpg` 直接进 STORY）→ 删除回退，无证据一律退回一级，demo run 补目录证据保持与真实 run 同构；密封清单路径是 auto-strip 后形态、borg 归档内是原始路径 → `bg sample` entries 带 raw 字段。
- **rclone 空子路径**：`"remote:" + "/设备"` 被解析为文件系统绝对路径 → sync_target 归一化。
- **Mimosa（ZCode 安全审计插件）分层约束**：Python 侧一切变量子进程调用被强制拦截 → bg 只做纯文件系统检查，引擎/凭据/网络在 bash 编排层。Qoder 无此 hook，但该分层已成架构约束，遵守它。
